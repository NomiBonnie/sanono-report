> 2026 年 4 月初，Andrej Karpathy 在 GitHub 发布了一篇名为《LLM Wiki》的 Gist。这位斯坦福计算机视觉博士、OpenAI 联合创始人、前特斯拉 AI 总监，用一份 2000 多字的"idea file"描述了一个看似简单、实则颠覆的知识管理方案。这篇文章迅速在技术圈引爆，在 X 上获得 2.2 万点赞，无数人开始复刻和实践。它不是一个产品发布，也不是一篇学术论文，而是一个正在被 Karpathy 本人使用的真实工作流——用 LLM 来维护个人知识库。
>
> 如果你是知识工作者——设计师、研究员、产品经理、工程师——这篇文章与你的关系比你想象的更直接。你现在使用的笔记软件，可能即将过时。不是因为功能不够强大,而是因为**维护者变了**。过去你自己整理文件夹、打标签、写摘要、建立交叉引用;现在这些工作可以交给 AI。从"人工维护的静态笔记本"到"AI 持续编译的动态知识图谱",这不是工具的升级,是范式的转换。
>
> Karpathy 方案的核心洞察在于:**知识库的价值不在于存储,而在于连接**。传统 RAG(检索增强生成)每次查询都从零开始拼凑答案;LLM Wiki 则让 AI 像图书管理员一样,把每一篇新文档整合进现有知识网络,更新相关词条,标记矛盾,补充交叉引用。知识不是被动存储,而是主动生长。这个想法并不新——1945 年 Vannevar Bush 就构想过 Memex,1960 年代 Niklas Luhmann 用卡片盒实践过——但 LLM 第一次让"零成本维护"成为现实。

## 一、从 Memex 到 LLM Wiki:八十年的知识管理梦

1945 年 7 月,《大西洋月刊》发表了 Vannevar Bush 的《诚如所思》(As We May Think)。这位二战期间领导美国科研的工程师描绘了一个叫 **Memex** 的装置:一张桌子,里面存储着微缩胶片,使用者可以在文档之间建立"联想轨迹"(associative trails),让知识像人脑一样通过连接而非分类来组织。Bush 写道:**"人类的思维不是按照字母顺序或数字顺序运作的,而是通过联想跳跃。"**

这个构想影响了之后几十年的计算机发展——超文本、万维网、维基百科,都是 Memex 精神的延续。但 Bush 遇到的问题一直没有解决:**谁来维护这些连接?**

1960 年代,德国社会学家 **Niklas Luhmann** 给出了他的答案:卡片盒笔记法(Zettelkasten)。Luhmann 用 9 万张卡片建立了一个模拟超文本系统,每张卡片通过编号系统指向其他卡片,形成一个自组织的知识网络。他说:**"我的卡片盒是我的合作者。"** 他用这套系统在 30 年间出版了 70 本书和 400 多篇论文。

但这套方法的代价是巨大的。Luhmann 每天花数小时维护卡片盒——写新卡片、更新旧卡片、调整编号、建立交叉引用。**知识管理的价值与维护成本之间,始终存在一道难以逾越的鸿沟。**

2000 年代,数字笔记软件试图降低这个成本。Evernote、Notion、Roam Research、Obsidian,每一代工具都承诺"更容易的知识管理"。但本质上,它们只是把纸质卡片换成了电子文档,**维护者仍然是人**。

2020 年,Tiago Forte 出版《Building a Second Brain》,提出 PARA 方法(Projects / Areas / Resources / Archives),试图用更科学的文件夹结构来降低维护成本。但即便是最狂热的 Second Brain 践行者,也承认:**笔记系统最终都会腐烂**。因为人会累、会忘、会懒,而知识图谱需要持续的、无聊的、机械的维护工作。

直到 2026 年,Karpathy 的 LLM Wiki 方案出现,这道八十年的难题第一次有了可行解:**让 AI 成为维护者**。

人负责阅读、思考、提问;AI 负责摘要、交叉引用、一致性检查。**维护成本降到接近零,知识图谱终于可以持续生长。**

*从 1945 年 Bush 的 Memex 设想,到 2026 年 Karpathy 的 LLM Wiki,八十年的知识管理演化史*


## 二、Karpathy 的三层架构:Raw、Wiki、Schema

Karpathy 方案的技术架构出人意料地简洁。没有向量数据库,没有 embedding pipeline,没有复杂的 RAG 基础设施。整个系统只有三层,每层职责清晰:

**第一层:Raw Sources(原始素材)**

这一层是你的个人数据仓库——文章、论文、图片、数据文件,以原始格式存放。Karpathy 用 Obsidian Web Clipper 把网页文章转成 Markdown 格式,用快捷键把图片下载到本地,确保 LLM 可以直接读取。

关键原则:**Raw 目录是不可变的**。LLM 只从这里读取,永远不修改。这保证了信息溯源——任何 wiki 页面的任何观点,都可以追溯到 raw/ 下的某份原始文档。

**第二层:Wiki(知识图谱)**

这一层完全由 LLM 拥有和维护。当你添加一篇新文章到 raw/ 目录,LLM 不只是建索引——它会阅读全文,提取关键信息,然后执行一连串操作:

- 生成摘要页面
- 创建或更新相关实体页面(人物、概念、产品)
- 在已有页面中添加交叉引用链接
- 标记新信息与旧内容之间的矛盾
- 更新总索引(index.md)和操作日志(log.md)

**一篇新文档可能触发 10 到 15 个 wiki 页面的更新**。这种"一次摄入、多点扩散"的模式,正是传统笔记软件做不到的——你可能记住了在某篇文档里写的内容,但你不会手动更新其他十个相关页面。

Karpathy 描述他的工作方式:"我一边开着 LLM agent,一边开着 Obsidian。LLM 基于我们的对话做修改,我实时浏览结果——跟踪链接、查看图谱视图、阅读更新的页面。**Obsidian 是 IDE,LLM 是程序员,wiki 是代码库。**"

这个类比精确地捕捉了角色分工:人类是项目经理(决定方向),LLM 是执行者(处理细节),wiki 是持续演化的产品。

**第三层:Schema(规范文档)**

这一层类似于编程中的配置文件——一份告诉 LLM 如何组织 wiki 的说明书。比如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md。它定义了:目录结构的约定、页面格式的规范、摄入新文档的工作流程、回答问题的策略。

Karpathy 对 Schema 的定位很有意思:它不是一次性写好的静态文件,而是**你和 LLM 共同演化的产物**。随着你使用 wiki 的经验积累,Schema 会不断更新——哪些约定有用,哪些需要调整,什么工作流效率最高。Schema 本身也在"生长"。

三层之间的关系可以用一个比喻来理解:Raw 是矿石,Wiki 是提炼后的金属制品,Schema 是冶炼手册。**矿石不会被改动,制品随时在更新,手册记录了最佳实践。**

![](/images/reading/karpathy-llm-wiki-2.jpg)

*三层架构:底层是不可变的原始素材,中层是 LLM 维护的知识图谱,顶层是共同演化的规范文档*

这个架构还隐含了两种重要的操作模式:

**摄入(Ingest)**:每次添加新素材时触发。LLM 读取原文,与你讨论要点,然后系统性地更新 wiki 的多个页面。Karpathy 说他偏好一次只摄入一篇文档,边摄入边参与——"我读摘要、检查更新、引导 LLM 强调什么"。但批量摄入也是可行的。

**健康检查(Lint)**:定期让 LLM 扫描 wiki,寻找:页面之间的矛盾、被新数据推翻的旧结论、没有任何入链的孤岛页面、被提及但没有独立页面的重要概念、缺失的交叉引用。**LLM 甚至会建议你去搜索新的资料来填补空白**——wiki 不只是被动存储,它在主动生长。


## 三、交叉引用:为什么 [[wikilinks]] 是灵魂

在 Karpathy 的方案里,知识图谱中最有价值的不是单个页面的内容,而是**页面之间的链接**。

这个观点并不新。早在 1945 年,Bush 就指出 Memex 的精髓在于"联想轨迹"。Luhmann 也说过:"每张卡片只是网络中的一个节点,它的质量取决于引用和反向引用。" 但在数字笔记的实际操作中,交叉引用一直是最被忽视的部分。

原因很简单:**手动维护交叉引用太累了。**

你在 A 页面写了一个概念,B 页面提到了同样的概念,C 页面引用了 A 的结论。如果你手动管理这些链接,每增加一篇文档就需要回顾所有可能相关的已有页面,检查是否需要添加新的链接。当文档数量超过 50 篇时,这项工作变得不可能。

Obsidian 的 `[[wikilinks]]` 语法提供了一个低门槛的解决方案——只需输入双括号和页面名称,就可以创建双向链接。Obsidian 的图谱视图(graph view)让你看到整个知识网络的拓扑结构:哪些页面是枢纽,哪些是孤岛,哪些区域连接密集,哪些稀疏。

但 wikilinks 的作用远不止导航。**当 LLM 读取一个包含 wikilinks 的 wiki 时,它获得的不是一堆独立的文档,而是一个语义网络。** 链接本身就是信息——A 链接到 B 意味着 A 和 B 之间存在某种关系,LLM 可以理解并利用这种关系来回答问题。

Karpathy 在原文中提到了两个特殊文件来辅助导航:

**index.md**:内容索引。每个 wiki 页面都列在其中,附带一行摘要和分类标签。LLM 回答问题时,首先读取 index.md 定位相关页面,然后深入阅读。Karpathy 发现,**在中等规模(约 100 篇文章、几百个页面)的知识库中,这种基于索引的导航比向量检索更有效**——不需要任何 embedding 基础设施。

**log.md**:操作日志。按时间顺序记录每次摄入、查询、健康检查。每条记录用统一前缀(如 `## [2026-04-02] ingest | 文章标题`),可以用 grep 等 Unix 工具快速筛选。日志提供了 wiki 的"演化时间线",让 LLM 了解最近做过什么。

VentureBeat 在报道中引用了社区成员 Charly Wargnier 的评价:**"它像一个活着的 AI 知识库,能自我修复。"** 这个"自我修复"的能力正是来自交叉引用——当你更新一个实体页面时,LLM 会检查所有链接到这个页面的其他页面,看看是否需要同步更新。没有链接,就没有这种级联修复的可能。

这也是 LLM Wiki 与传统 RAG 系统最根本的区别。**RAG 在查询时拼凑答案,LLM Wiki 在摄入时编译知识。** 前者每次从零开始,后者持续积累。前者的质量取决于检索算法,后者的质量取决于交叉引用的密度和准确性。

![](/images/reading/karpathy-llm-wiki-3.jpg)

*交叉引用将独立的文档变成一个有机的知识网络——连接即价值*


## 四、从理论到实操:三种落地方案

Karpathy 的 Gist 发布后,社区迅速涌现出各种实践方案。根据技术栈和使用场景的不同,大致可以分为三类。

### 方案一:Obsidian + AI 编程工具

这是目前最流行的实践路线,也是中文社区"老张"(@laozhang2579)推荐的方案。核心思路:用 Obsidian 作为 wiki 的浏览器和编辑器,用 Cursor 或 Claude Code 作为 LLM agent 来维护 wiki 文件。

工作流大致如下:

1. 用 Obsidian Web Clipper 把网页文章保存到 raw/ 目录
2. 在 Cursor 中打开整个 wiki 目录,让 AI 读取新文档
3. AI 生成摘要、更新索引、创建交叉引用
4. 在 Obsidian 中浏览结果,通过图谱视图检查连接质量

老张在 X 推文中分享了他的实操经验,强调了几个关键细节:

首先是 **Schema 文件的重要性**。他发现不写 Schema(即 AGENTS.md 或 CLAUDE.md),LLM 的输出质量会显著下降——没有规范的 LLM 就像没有编码规范的实习生,代码能跑但风格混乱。

其次是 **摄入节奏**。老张建议每次只处理一篇文档,与 AI 充分讨论后再处理下一篇。批量摄入虽然效率高,但质量难以保证,容易出现 AI 敷衍了事的情况。

**优势**: Obsidian 的生态系统成熟——图谱视图、Dataview 查询插件、Marp 幻灯片插件——能让 wiki 的可视化和交互性大幅提升。Lex Fridman 在回应 Karpathy 时提到,他会让 LLM 生成动态 HTML 页面来可视化数据,甚至在 7-10 英里的跑步中通过语音与"临时知识库"对话。

**劣势**: 依赖多个工具的配合(Obsidian + Cursor/Claude Code + 命令行),有一定技术门槛。而且 Cursor 和 Claude Code 都有 token 限制,处理大规模 wiki 时可能需要频繁分段。

### 方案二:纯 Markdown + CLI Agent

这是 Karpathy 自己使用的方案,也是最极简的路线。不需要任何特定的笔记软件,整个 wiki 就是一个包含 Markdown 文件的 Git 仓库,用命令行工具和 LLM API 来操作。

Karpathy 坦承这目前还是"一堆 hacky 脚本的集合"。但他提到了一个值得注意的工具:**qmd**——一个本地 Markdown 搜索引擎,结合了 BM25 和向量检索,支持 LLM 重排序,完全在设备端运行。它同时提供 CLI 和 MCP server 接口,LLM 可以直接调用。

**优势**: 不依赖任何特定软件,**wiki 就是 Git 仓库**——自动获得版本历史、分支管理、协作能力。部署极度灵活,可以在任何有命令行的环境中运行。

**劣势**: 没有图谱视图等可视化功能,纯文本操作对非技术用户不友好。需要自己搭建 LLM agent 的集成,入门成本高。

### 方案三:Agent-native 平台

这是最激进的路线——使用专门为 AI agent 设计的平台,让 LLM Wiki 成为平台的原生能力而非需要手动搭建的工作流。

X 用户 @jumperz(Secondmate 创始人)展示了一个用 OpenClaw 编排的"群体知识库"(Swarm Knowledge Base)方案:10 个 AI agent 协作,每个 agent 负责不同领域,共享同一个 wiki。一个独立的"质量门卫"agent(基于 Hermes 模型)负责审核每篇新增页面,只有通过验证的内容才能进入正式 wiki。

**这个方案解决了多 agent 协作中的核心问题:一个 agent 的幻觉不会污染整个知识库。** 质量门卫形成了一个"编译循环":agents 产出原始内容→编译器组织结构→Hermes 验证真实性→验证通过的简报反馈给所有 agent。每个 agent 每次"醒来"时,看到的都是经过过滤的、高可信度的集体知识。

企业家 Vamshi Reddy 在 X 上评论说:**"每个企业都有一个 raw/ 目录。没有人编译过它。这就是产品机会。"** Karpathy 对此表示同意,认为这代表了一个"不可思议的新产品品类"。

Edra 联合创始人 Eugen Alpeza 指出了企业落地的挑战:"从个人研究 wiki 到企业运营之间的跳跃是残酷的。数千名员工、数百万条记录、各团队之间相互矛盾的部落知识。"

三种方案并不互斥。你完全可以从方案一入手(最低门槛),随着需求增长逐步迁移到方案二或方案三。

![](/images/reading/karpathy-llm-wiki-4.jpg)

*从个人笔记到多 agent 协作:三种落地方案覆盖了从入门到企业级的完整光谱*


## 五、反面论证:五个不能忽视的隐患

任何值得认真对待的技术方案都需要反面论证。LLM Wiki 不是银弹,在实践中至少面临五个严肃的问题。

### 隐患一:幻觉污染

LLM 会编造事实,这已经不是新闻。但在 LLM Wiki 的语境下,幻觉的危害被放大了。

传统 RAG 系统中,LLM 的幻觉只影响单次回答——你关掉窗口,幻觉就消失了。但在 LLM Wiki 中,**幻觉可能被写入 wiki 页面,成为持久化的"知识"**,并通过交叉引用传播到其他页面。一个错误的概念定义可能被 10 个其他页面引用,形成级联污染。

2026 年 3 月,Wikipedia 的案例提供了现实警示。Open Knowledge Association 使用 AI 翻译维基百科文章,结果引入了大量幻觉——虚假引用、错误事实、凭空捏造的来源。维基百科编辑社区不得不出台新政策来限制 AI 翻译。**如果公共百科全书都无法避免 AI 幻觉,个人知识库更难幸免。**

Karpathy 方案中的 lint(健康检查)机制是对此的部分应对——定期让 LLM 自查矛盾和不一致。但让同一个 LLM 检查自己写的内容,有点像让学生批改自己的试卷。Secondmate 的"质量门卫"方案(用独立模型审核)是一个更可靠的思路,但增加了系统复杂度和运行成本。

### 隐患二:认知外包

当 AI 承担了所有的摘要、整理、交叉引用工作后,人类还能保持对知识的深度理解吗?

Luhmann 的卡片盒方法之所以有效,部分原因在于手动整理本身就是一种思考过程。**你在决定一张卡片放在哪里、和哪些卡片链接时,实际上是在进行一次概念辨析。** 这个"摩擦力"不是 bug,而是 feature。

Tiago Forte 在 2026 年推出了"AI Second Brain"课程,但他同时指出了一个关键区别:**个人知识管理(PKM)正在被个人上下文管理(PCM)取代——新的瓶颈不是 AI 的能力,而是你给 AI 提供正确信息的能力。** 换句话说,当 AI 处理一切时,你的价值在于判断力,而判断力来自深度理解,深度理解来自与知识的"摩擦"。

如果 LLM Wiki 让你彻底脱离了这种摩擦,你可能拥有一个庞大的知识库,却对其中的内容一知半解。

### 隐患三:隐私和安全

Karpathy 方案的核心是让 LLM 读取你的全部原始素材——研究论文、个人笔记、商业文档。如果使用云端 LLM(如 GPT-4、Claude),**你的整个知识库都在通过 API 传输**。

对于个人用户,这意味着你的阅读历史、研究方向、甚至思维模式都可能被记录在 API 日志中。对于企业用户,合规风险更大——内部文档通过第三方 API 传输可能违反数据保护法规。

Karpathy 提到的 qmd 工具(本地搜索引擎)是一个缓解措施——它完全在设备端运行。但 wiki 的生成和维护仍然依赖远程 LLM。完全的本地化方案(如使用 Llama 等开源模型)可以解决隐私问题,但目前本地模型在长文本理解和交叉引用方面的能力还不够。

### 隐患四:规模天花板

Karpathy 坦言,他的方案在约 100 篇文章、40 万字的规模下工作良好。这对个人研究项目够用了,但企业知识库动辄数百万份文档。

当 wiki 页面数量超过几千个时,基于 index.md 的导航策略会失效——一个 index 文件装不下所有页面的摘要。此时仍然需要回到 embedding + 向量数据库的方案,**LLM Wiki 并没有消灭 RAG,只是在中小规模下提供了一个更简洁的替代选项**。

Reddit 的 LocalLLaMA 社区在讨论这个问题时,有人指出:"Karpathy 可能发现了正确的思路,但它不能利用用户交互生成的'快速'推理结果。" 也就是说,wiki 只捕获了摄入阶段的知识编译,**日常问答中产生的新洞察和推理链条可能没有被回写到 wiki 中**。

### 隐患五:维护者单点故障

Karpathy 写道:"你很少手动编辑 wiki——那是 LLM 的领地。" 这意味着 wiki 的质量完全取决于 LLM 的能力和 Schema 的设计。

如果某天 LLM 提供商更改了 API、提高了价格,或者某个模型版本在知识整理方面出现退化(这在模型更新中并不罕见),**你的整个知识管理系统可能突然降级**。你拥有所有的 Markdown 文件(这是好的——可审计、可读),但你可能失去了维护它们的能力。

这也是为什么 Schema 层如此重要。一个写得好的 Schema 可以让你在不同 LLM 之间切换时,保持 wiki 的一致性和质量。**Schema 是对 LLM 的编程,wiki 是编程的产物。**

*AI 图书管理员面临的挑战:幻觉、认知外包、隐私、规模和单点依赖*


## 六、对知识工作者的启示

读完 Karpathy 的方案和社区的各种实践后,我认为不同人群应该采取不同的行动:

### 应该立即行动的人

**研究人员和分析师**。如果你的工作是长周期、深度积累型的——跟踪某个领域数月甚至数年,持续阅读论文、报告、新闻——LLM Wiki 可能是你当前能采用的最高效知识管理方案。传统笔记软件在这种场景下的痛点最突出:文档越多,越难找到关联,越懒得维护,知识库越来越像数字垃圾场。

**产品经理和设计师**。你们的工作本质上是信息综合——把竞品分析、用户研究、技术趋势、业务指标编织成一个连贯的产品策略。这正是 LLM Wiki 最擅长的:把碎片化的输入编译成结构化的知识网络。

**独立创作者和 Newsletter 作者**。你需要持续阅读、持续积累素材、持续产出。一个由 AI 维护的知识库可以成为你的永久性素材库,每一次阅读都在为未来的文章储备弹药。

### 可以观望的人

**日常笔记用户**。如果你的需求只是记个待办、存个书签、偶尔写几段感想,现有工具(Apple Notes、Notion)完全够用。LLM Wiki 的优势在"编译"和"交叉引用",如果你的笔记之间没有太多关联需求,引入 LLM 维护是过度工程。

**对 AI 输出质量有严格要求的场景**。法律、医疗、财务等领域,一个幻觉可能造成严重后果。在这些领域使用 LLM Wiki,需要极其严格的审核流程,成本可能高于收益。

### 所有人都应该思考的问题

无论你是否立即采用 LLM Wiki,有一个更深层的问题值得思考:**当 AI 能帮你管理知识时,你的核心竞争力是什么?**

Karpathy 的答案隐含在他的方案设计中:人负责"sourcing, exploration, and asking the right questions"(策展、探索和提出正确的问题)。**阅读什么、关注哪个方向、问出什么问题——这些判断力才是不可替代的**。知识管理的体力劳动(摘要、分类、链接、一致性检查)可以外包给 AI,但知识管理的脑力劳动(策展眼光和提问质量)只属于你。

这与 Forte 的"个人上下文管理"观点不谋而合。**AI 时代的知识工作者,核心技能不再是"整理信息",而是"为 AI 提供正确的上下文"。**

## 七、结语

Karpathy 在 Gist 的最后写道,这份文档是"故意抽象的"——它描述的是模式(pattern),不是实现(implementation)。目录结构、页面格式、工具选择,都可以根据你的领域和偏好来决定。

这种开放性本身就是方案的一部分。LLM Wiki 不是一个产品,不是一个框架,**它是一种思维方式的转变:从"我手动维护笔记"到"AI 持续编译我的知识"**。

八十年前,Bush 设想了 Memex,但找不到维护者。六十年前,Luhmann 找到了维护者——他自己,但代价是每天数小时的手工劳动。今天,LLM 第一次让"零成本维护的个人知识图谱"成为现实。

Karpathy 用一句话总结了核心精神:**"知识管理中令人厌倦的部分不是阅读和思考,而是记账——更新交叉引用、保持摘要更新、标记新旧数据的矛盾、在几十个页面之间维持一致性。人类放弃 wiki 是因为维护成本增长得比价值更快。LLM 不会厌倦,不会忘记更新一个交叉引用,可以在一次操作中触及 15 个文件。"**

你的下一个知识管理系统,可能不需要你维护。
