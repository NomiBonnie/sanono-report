# 智能体工程的 8 个段位 — Bassim Eledath

> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个段位里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

---

AI 写代码的能力，已经跑在了大多数人驾驭它的能力前面。所以你会看到一个奇怪的现象：SWE-bench（AI 编码能力评测基准）的分数一路狂飙，但工程团队真正关心的生产力指标却没怎么动。Anthropic 的团队用 10 天就把 Cowork（他们的 AI 协作产品）给发布了，而另一个团队拿着同样的模型，连一个 POC 都搞不定。差别不在模型，在于一个团队已经把"会用"这件事跑通了，另一个还没有。

这个差距不会一夜之间消失，它是一级一级缩小的。一共 8 级。读到这里的你大概已经过了前几级，但你应该急着往上走，因为每往上一级都是输出量的巨大飞跃，而且模型能力每进步一点，这些收益还会被进一步放大。

还有件事你可能没想到：你的效率不只取决于自己。假设你已经是 Level 7 的高手，睡觉的时候后台智能体在帮你提 PR。但如果你的仓库需要同事审批才能合并，而那位同事还停在 Level 2，手动一个个审 PR，你的速度就被他拖住了。所以把队友拉上来，其实是在帮自己。

在和很多实践 AI 辅助编码的团队和个人交流之后，我总结出了这 8 个递进的段位。顺序不是严格线性的，但大致如此。

## 第 1&2 级：Tab 自动补全与 Agent IDE

![Levels 1 & 2](/images/reading/agentic-engineering-2.jpg)

这两级我快速带过，主要留个记录。不感兴趣可以直接跳过。

最早是 Copilot 和 Tab 自动补全。按一下 Tab，代码就自动补完了。很多人可能已经忘了这件事，新入行的人甚至直接跳过了这一步。这个阶段比较偏好有经验的开发者，他们能先搭好代码骨架，再让 AI 来填空。

后来 Cursor 这样的 AI 原生 IDE 改变了游戏规则。它把聊天和代码库连了起来，多文件编辑一下子变得轻松很多。但天花板始终是上下文：模型只能基于它能看到的东西来帮你，而它经常要么看不到关键信息，要么看到一堆不相关的噪音。

大多数处于这个阶段的人也在尝试计划模式（plan mode），就是先把一个粗略的想法变成一步步的结构化计划给 LLM，反复调整这个计划，然后再触发实现。在这个阶段这么做挺管用的，也是保持掌控感的好办法。不过后面几级你会发现，对计划模式的依赖会越来越少。

## 第 3 级：上下文工程 Context Engineering

![Context Engineering](/images/reading/agentic-engineering-3.jpg)

2025 年的年度热词。上下文工程之所以成为一门技术，是因为模型终于能在合适的上下文量下，可靠地执行合理数量的指令了。噪音太多和信息太少一样糟糕，所以核心功夫在于提升每个 token 的信息密度。当时的口号是"每个 token 都得拼命争取自己的位置"。

实际操作中，上下文工程涉及的面比大多数人以为的要广。它包括你的系统提示词和规则文件（.cursorrules、CLAUDE.md 这些）。它包括你怎么描述工具，因为模型是通过读工具描述来决定调用哪个的。它包括管理对话历史，让一个跑了很多轮的 Agent 不会在第十轮的时候忘了前面在干嘛。它还包括决定每一轮暴露哪些工具给模型，因为选项太多会让模型和人一样不知所措。

现在你可能觉得上下文工程没那么热了。确实，天平已经倾向于那些能容忍更多噪音、在更混乱场景中依然能推理的模型，更大的上下文窗口也有帮助。但注意上下文消耗的问题仍然存在。

比如，小模型对上下文更敏感。语音应用经常用小模型，而且上下文大小和首 token 延迟直接相关，影响响应速度。再比如，有些工具和模态特别烧 token。像 Playwright 的 MCP 和图片输入，消耗 token 的速度极快，会让你在 Claude Code 里比预期更早进入"compact session"状态（一种上下文被压缩的机制）。还有，当 Agent 能调用几十个工具时，模型花在解析工具 schema 上的 token 比真正干活的还多。

所以上下文工程并没有消失，只是进化了。重心从"过滤掉坏上下文"变成了"确保对的上下文在对的时间出现"。而这个转变，正好为第 4 级铺好了路。

## 第 4 级：复利工程 Compounding Engineering

![Compounding Engineering](/images/reading/agentic-engineering-4.jpg)

上下文工程让当前这一次会话变得更好。复利工程让之后的每一次会话都变得更好。Kieran Klaassen 把这个理念带火了，对我和很多人来说都是一个转折点，让我们意识到"凭感觉编程"（vibe coding）不只是能做原型，能做的远比想象中多。

它是一个"计划、委派、评估、固化"的循环。你给任务规划足够的上下文让 LLM 能成功完成，然后把任务交出去，评估产出，最后也是最关键的一步：把学到的东西固化下来。什么管用、什么出了问题、下次该遵循什么模式，全都记下来。

这个"固化"步骤才是让工程成果像复利一样累积的关键。LLM 是无状态的。你昨天明确删掉的一个依赖，它明天还会给你加回来，除非你告诉它别这么做。最常见的做法是更新你的 CLAUDE.md（或者对应的规则文件），把教训写进去，这样之后的每次会话都能受益。不过有个注意事项：什么都往规则文件里塞的冲动会适得其反，指令太多等于没有指令。更好的做法是创造一个环境，让 LLM 能自己找到有用的上下文，比如维护一个时刻更新的 docs/ 文件夹，这一点在第 7 级会进一步展开。

真正在做复利工程的人，通常对喂给 LLM 的上下文极其敏感。当 LLM 犯了错，他们的第一反应是"是不是上下文没给对"，而不是"模型不行"。这种直觉，正是让第 5 到第 8 级成为可能的基础。

## 第 5 级：MCP 与技能 MCP and Skills

![MCP and Skills](/images/reading/agentic-engineering-5.jpg)

第 3 和第 4 级解决的是上下文问题。第 5 级解决的是能力问题。MCP（Model Context Protocol，模型上下文协议）和自定义技能让你的 LLM 能够接入数据库、API、CI 流水线、设计系统，能用 Playwright 做浏览器测试，能通过 Slack 发通知。模型不再只是对着代码库想想，现在它可以直接动手了。

关于 MCP 和技能的好资料已经很多了，我就不重复基础概念。但分享一下我实际怎么用的：我们团队共享了一个 PR 审查技能，大家一起迭代打磨（到现在还在改），它会根据 PR 的性质有条件地启动不同的子智能体。一个负责数据库集成安全检查，一个跑复杂度分析来发现冗余或过度设计，一个检查 prompt 健康度确保格式符合团队规范，另外还会跑 linter 和 Ruff。

为什么在审查技能上投入这么多？因为智能体开始批量产出 PR 之后，靠人审代码已经跟不上了，反而成了拖后腿的环节。Latent Space（AI 领域知名播客）提出了一个很有说服力的观点：传统意义上的代码审查已经死了，取代它的是自动化、一致性、技能驱动的审查。

MCP 方面，我用 Braintrust 的 MCP 让 LLM 能查询评估日志并直接做修改。我用 DeepWiki MCP 让智能体可以访问任意开源仓库的文档，而不需要手动把文档拉进上下文。

当团队里多个人开始各写各的同类技能时，就该整合成一个共享注册中心了。Block（节哀顺变）在这方面有篇很好的文章：他们搭建了一个内部技能市场，里面有超过 100 个技能，还按角色和团队分了精选包。技能和代码享受同样的待遇：提 PR、审查、版本管理。

还有一个趋势正在加速：LLM 越来越多地使用 CLI 工具而不是 MCP。好像每家公司都在出自己的 CLI：Google Workspace CLI、Braintrust 也即将推出一个。原因是 token 效率。MCP 服务在每一轮都会把完整的工具 schema 注入上下文，不管 Agent 用不用得到。CLI 反过来：Agent 执行一个精确的命令，只有相关的输出进入上下文窗口。我大量使用 agent-browser 正是因为这个原因，而不是用 Playwright MCP。

在继续之前要说一件重要的事。**第 3 到第 5 级是后面所有级别的基石。** LLM 在某些事上好得出奇，在另一些事上又差得离谱，你需要培养出一种直觉来感知这些边界，然后再往上叠加更多自动化。如果你的上下文是噪音，prompt 没写到位或者写偏了，工具描述也马马虎虎，那第 6 到第 8 级只会把这些问题放大。

## 第 6 级：工程脚手架与自动反馈循环 Harness Engineering

![Harness Engineering](/images/reading/agentic-engineering-6.jpg)

火箭真正点火了。

上下文工程管的是模型看到什么。工程脚手架管的是整个环境、工具链和反馈回路，让智能体在你不介入的情况下也能可靠地完成工作。不是只给 Agent 一个编辑器，而是给它完整的反馈闭环。

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航全部接入了 Agent 运行时，这样 Agent 就能截屏、驱动 UI 操作、查日志、验证自己的修复。给一个提示词，Agent 就能复现一个 bug、录一段视频、实现修复。然后它自己驱动应用来验证，开一个 PR，回应审查意见，合并代码，只在需要人做判断的时候才把问题交上来。Agent 不只是写代码，它能看到代码跑出来的效果并且迭代改进，就像人会做的那样。

我的团队做的是技术排障方面的语音和聊天智能体，所以我写了一个叫 converse 的 CLI 工具，让任何 LLM 都能和我们的后端端点进行多轮对话。LLM 改完代码之后用 converse 对着线上系统测试对话效果，然后迭代。有时候这种自我改进循环会连续跑好几个小时。当结果可验证的时候，这种模式特别强大，比如对话必须走这个流程、必须在这些情况下调用这些工具（比如转人工）。

让这一切成为可能的核心概念叫反压（backpressure）：类型系统、测试、linter、pre-commit hooks（代码提交前的自动检查），这些自动反馈机制让 Agent 能在不需要人介入的情况下发现和纠正错误。**要自主就必须有反压，否则就是垃圾生产线。** 安全方面也一样。Vercel 的 CTO 提出，Agent、它生成的代码和你的密钥应该放在不同的信任域里。因为如果一个藏在日志文件里的提示注入（prompt injection）骗了 Agent，而所有东西又在同一个安全上下文里，你的凭证就可能被偷走。安全边界也是一种反压：它限制的是 Agent 失控时能做什么，而不仅仅是它应该做什么。

两个实用建议。第一，为吞吐量设计而不是为完美设计。当你要求每次提交都完美时，多个 Agent 会扎堆在同一个 bug 上互相覆盖修复。更好的做法是容忍小的非阻塞性错误，在发布前做一次统一的质量检查。我们对人类同事也是这么做的。第二，约束比指令好用。那种"先做 A，再做 B，再做 C"的步骤式 prompt 正在过时。我的经验是，定义边界比给清单管用，因为 Agent 会死盯着清单上的条目，忽略清单之外的一切。更好的 prompt 是"这是我要的结果，你自己想办法，跑过所有这些测试就算成功"。

工程脚手架的另一半，是确保 Agent 不需要你就能在仓库里自由导航。OpenAI 的做法是：把 AGENTS.md 控制在大约 100 行，当作一个目录，指向其他地方的结构化文档。而且文档新鲜度要纳入 CI，而不是靠临时更新，因为临时更新迟早会过期。

当你把这些都搭好之后，一个自然的问题就冒出来了：如果 Agent 能自己验证工作、在仓库里自由穿行、自行纠错，你为什么还要坐在椅子上盯着？

## 第 7 级：后台智能体 Background Agents

![Background Agents](/images/reading/agentic-engineering-7.jpg)

一个大胆判断：计划模式正在走向消亡。

Boris Cherny，Claude Code 的创造者，今天仍然有 80% 的任务是从计划模式开始的。但每一代新模型出来，经过计划之后的一次性成功率都在攀升。我觉得我们正在接近一个临界点：计划模式作为一个需要人参与的独立步骤将会淡出。不是因为规划不重要了，而是模型自己规划的能力越来越强了。不过有个大前提：这只在你把第 3 到第 6 级的功课都做好了之后才成立。上下文干净、约束明确、工具描述到位、反馈循环紧凑，模型才能在不需要你审核的情况下可靠地规划。如果这些没做好，你还是得盯着计划。

说清楚一点，规划作为一种通用实践并没有消失，只是换了形态。对新手来说，计划模式仍然是正确的起点（如第 1 和第 2 级所述）。但到了第 7 级处理复杂功能时，"规划"看起来不再是写一份分步大纲，而更像是探索：探测代码库、在 worktree（Git 工作树）里做原型、摸清解决方案的空间。而且越来越多的时候，这种探索是后台智能体在帮你做。

这很重要，因为这正是后台智能体得以成立的前提。如果 Agent 能生成一个靠谱的计划并且不需要你签字就能执行，它就可以异步运行，你去做别的事。这才是关键的转变：从"我同时在切好几个标签页"到"有些工作在没有我的情况下在推进"。

Ralph Loop 是最常见的入门模式：一个自主 Agent 循环反复运行编码 CLI 直到 PRD（产品需求文档）里的所有条目都完成，每次迭代都生成一个新实例并带着干净的上下文。我的经验是，要把 Ralph Loop 跑好非常难，PRD 里任何没写清楚或写偏了的地方都会反噬。这个模式有点太"扔出去就不管"了。

你可以并行跑多个 Ralph Loop，但 Agent 数量一上去，你会发现你的时间其实花在了协调上：排工作顺序、检查产出、推一把卡住的任务。你已经不在写代码了，你变成了中层管理者。你需要一个编排 Agent 来处理调度，这样你才能专注于意图而不是后勤。

我一直在用的工具叫 Dispatch，这是我写的一个 Claude Code 技能，能把你的会话变成一个指挥中心。你待在一个干净的主会话里，工作者 Agent 在隔离的上下文中干活。调度器负责规划、委派和追踪，你的主上下文窗口就留给了编排。当某个工作者卡住时，它会浮出一个澄清问题来问你，而不是默默地失败。

Dispatch 跑在本地，所以特别适合你想紧贴工作的快速开发场景：反馈更快、调试更方便、不需要搭基础设施。Ramp Inspect 是另一个互补的方案，适合跑得更久、更自主的工作：每个 Agent 会话都在云端的沙盒虚拟机里启动，包含完整的开发环境。一个产品经理在 Slack 里标记了一个 UI bug，Inspect 就接手跑起来了，你的笔记本电脑合着都行。代价是运维复杂度更高（基础设施、快照、安全），但你换来的是本地 Agent 给不了的规模化和可复现性。我建议两个都用。

在这个级别还有一个出奇好用的模式：**给不同的任务用不同的模型。** 最好的工程团队不是由一群一模一样的人组成的，而是由思维方式不同、经验各异、各有所长的人组成的。LLM 也一样。这些模型经过不同的后训练，性格倾向真的不同。我经常把 Opus 分配给实现、Gemini 分配给探索性研究、Codex 分配给审查，综合产出比任何单一模型独立工作都要强。你可以理解为群体智慧，只不过用在代码上。

还有一点至关重要：**你必须把实现者和审查者分开。** 我在这上面吃过太多亏了。如果同一个模型实例既做实现又评估自己的工作，它是有偏见的。它会忽略问题，告诉你所有任务都完成了，但其实没有。这不是恶意，道理跟你不会给自己批卷子是一样的。让另一个模型（或者一个带审查专用 prompt 的不同实例）来做评审，你获取信号的质量会大幅提升。

后台智能体还打开了把 CI 和 AI 结合起来的大门。一旦 Agent 能在无人值守的情况下运行，就从现有基础设施来触发它们：一个文档机器人在每次合并后自动重新生成文档并提 PR 来更新 CLAUDE.md（我们在用这个，省了大量时间）。一个安全审查器扫描 PR 并提交修复。一个依赖升级机器人真正去升级包并跑测试套件，而不是只标记一下。好的上下文、复利规则、称手的工具、自动反馈循环，现在全都在自主运行。

## 第 8 级：自主多智能体协作 Autonomous Agent Teams

![Autonomous Agent Teams](/images/reading/agentic-engineering-8.jpg)

目前还没有人真正掌握这个级别，但有少数团队在往这个方向探索。这是当前的最前沿。

在第 7 级，你有一个编排 LLM 在中心辐射模式下给工作者 LLM 分配任务。第 8 级去掉了这个瓶颈。Agent 之间直接协调：认领任务、共享发现、标记依赖、解决冲突，不需要所有事情都经过一个中央编排器。

Claude Code 的实验性 Agent Teams 功能是一个早期实现：多个实例在共享代码库上并行工作，队友各自有自己的上下文窗口并且能直接互相通信。Anthropic 用 16 个并行 Agent 从零开始搭了一个能编译 Linux 的 C 编译器。Cursor 跑了数百个并发 Agent 持续数周，从零搭了一个浏览器并且把他们自己的代码库从 Solid 迁移到了 React。

但仔细看就会发现那些粗糙的接缝。Cursor 发现没有层级结构的话，Agent 会变得畏首畏尾，原地打转不出活。Anthropic 的 Agent 不断破坏已有功能，直到加了 CI 流水线来防止回退。所有在这个级别做实验的人都说了同一句话：多智能体协调是个极难的问题，目前没有人接近最优解。

我坦白说，我觉得模型还没准备好在大多数任务上达到这个级别的自主性。就算它们够聪明，速度还是太慢、token 消耗还是太大，在编译器和浏览器这种登月级项目之外并不经济（这些项目令人印象深刻，但离"好用"还远）。对我们日常的工作来说，第 7 级才是杠杆最大的地方。第 8 级最终可能会成为主流模式，这一点我不会意外，但现在我会把精力放在第 7 级上（除非你是 Cursor 这样的公司，突破本身就是你的业务）。

## 第 ? 级

不可避免的"下一步是什么"问题。

一旦你能顺畅地编排 Agent 团队，交互界面就没理由还停留在纯文本上。语音对语音（甚至可能是思维对思维？）地和你的编码 Agent 互动，用对话式的 Claude Code，而不只是语音转文字输入，这是一个自然的下一步。看着你的应用，大声描述一系列修改，然后看着它们在你眼前发生。

有一群人在追求完美的一次性生成：说出你想要的，AI 在一次 pass 中完美地完成。问题在于这个前提假设我们人类确切地知道自己想要什么。我们不知道。我们从来都不知道。软件开发一直是迭代的，我觉得永远都会是。只不过它会变得容易得多，远远超越纯文本交互，而且快得多。

所以：你在哪个段位？你在做什么来到达下一个？
