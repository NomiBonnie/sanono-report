> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个层级里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

# 智能体工程的 8 个层级

![The 8 Levels of Agentic Engineering](/images/reading/agentic-engineering-1.jpg)

AI 写代码的能力，已经远远甩开了我们驾驭它的能力。

SWE-bench 跑分一路飙升，可工程管理层真正在意的生产力指标纹丝不动，原因就在这儿。同样的模型，Anthropic 那边 10 天就把 Cowork 上了线，隔壁团队连一个 POC 都跑不通——**区别不在模型，在于一个团队打通了能力和实践之间那道坎，另一个没有。**

这道坎不会一步跨过去。它分 8 级。在座的大多数可能已经过了头两级，但你应该急着往上走——**每升一级，产出都是量级式的跳跃**，而且模型每进步一次，这些收益还会被进一步放大。

还有一个你该在意的理由：**组队效应**。你的产出比你以为的更依赖队友的段位。假设你已经到了 Level 7，夜里睡觉的时候后台智能体就把几个靠谱的 PR 提好了。可合并需要同事批准，偏偏这位同事还停在 Level 2，PR 一行行手动看——你的速度就被死死卡住了。**拉队友升级，就是在帮自己提速。**

跟好几个团队和个人聊过 AI 辅助编码的实战经验后，下面是我观察到的层级演进（不严格线性）：

## Level 1 & 2：Tab 补全与 AI IDE

这两级我快进，主要是为了完整性。可以随意略过。

一切始于 Copilot 和 Tab 补全。按一下 Tab，代码自动补完。很多人大概已经忘了这个阶段，后来入场的人更是直接跳过了。**这玩意儿对老手更友好**——你得先把骨架搭好，AI 才有东西可填。

以 Cursor 为代表的 AI IDE 改了游戏规则：聊天窗口直连代码库，**跨文件编辑的难度一下子降了一个数量级**。但天花板始终是上下文。模型只能帮到它「看得见」的部分，而恼人的是，它经常该看的没看到，不该看的看了一堆。

这个阶段大多数人也在折腾「计划模式」（Plan Mode）：把一个粗略的想法拆成结构化的步骤给 LLM，反复打磨计划，再触发执行。在这个阶段挺好使，也是维持掌控感的合理做法。不过后面几级对计划模式的依赖会越来越低。

## Level 3：上下文工程

![Context Engineering](/images/reading/agentic-engineering-2.jpg)

2025 年的年度热词。模型开始能在恰到好处的上下文下可靠地执行指令，这个概念就立住了。**上下文太嘈杂跟上下文不够一样糟**，核心功夫在于提升每个 token 的信息密度。当时的口号是：「每个 token 都得为自己在 prompt 里的位置拼命。」

实际操作中，上下文工程涉及的面比多数人意识到的要广。它涵盖系统提示和规则文件（.cursorrules、CLAUDE.md）；涵盖你怎么描述工具——模型读工具描述来决定调用哪个；涵盖对话历史的管理，别让长期运行的智能体聊了十轮就跑偏；还涵盖每一轮该暴露哪些工具——**选项太多模型会蒙，跟人一样。**

这个词如今提得没那么多了。天平倒向了那些能容忍更嘈杂上下文、在更混乱的场景里也能推理的模型（上下文窗口变大也帮了忙）。但留意什么在吃掉你的上下文，依然重要。几个还在踩坑的场景：

- **小模型对上下文更敏感。** 语音应用常用小模型，上下文大小还跟首 token 延迟挂钩，直接影响响应速度。

- **Token 吞噬大户。** 像 Playwright 这种 MCP（Model Context Protocol，模型上下文协议——一种让 AI 调用外部工具的标准协议）和图片输入会飞快地烧掉 token，让你在 Claude Code 里比预想的更早触发「精简会话」。

- **工具太多的智能体。** 模型花在解析工具定义上的 token 比干正事还多。

更本质的一点：**上下文工程没有消失，只是进化了。** 重心从「过滤掉坏的上下文」转向了「确保对的上下文在对的时机出现」。这个转变为 Level 4 铺了路。

## Level 4：复利工程

![Compounding Engineering](/images/reading/agentic-engineering-3.jpg)

上下文工程改善的是这一次会话。**复利工程改善的是以后每一次。**

这个概念由 Kieran Klaassen 推广开来，对我和很多人而言都是一个拐点——它证明了凭感觉编程（Vibe Coding）远不止能做原型。

它是一个「计划→委派→评估→固化」的循环。你为任务备好足够的上下文，让 LLM 成功完成；你把任务交出去；你评估产出；最后——**关键步骤——把经验固化下来：** 什么管用、什么出了岔子、下次该遵循什么模式。

「固化」这步才是它能产生复利的原因。LLM 没有记忆。昨天它重新引入了一个你明确删掉的依赖，明天它还会干——除非你告诉它别这么做。**最常见的办法是更新你的 CLAUDE.md**（或等价的规则文件），把教训烘焙进未来的每一次会话。但要小心：什么都往规则文件里塞的冲动会适得其反——指令太多跟没有一样。更聪明的做法是营造一个环境，让 LLM 自己就能轻松找到有用的上下文——比如维护一个时刻更新的 docs/ 文件夹（Level 7 会详说）。

**复利工程的实践者通常对输入给 LLM 的上下文极度敏感。** LLM 犯了错，他们第一反应是想「是不是缺了什么上下文」，而不是怪模型笨。这种直觉，是 Level 5 到 8 的地基。

## Level 5：MCP 与技能

Level 3 和 4 解决的是「看什么」的问题。**Level 5 解决的是「能做什么」。** MCP 和自定义技能（Skills）让你的 LLM 能触达数据库、API、CI 流水线、设计系统、Playwright 做浏览器测试、Slack 发通知。模型不再只是在脑子里琢磨你的代码库——**它现在能动手了。**

MCP 和 Skills 的入门介绍已经满天飞，我就不重复了。说几个我怎么用的：我的团队共享一个 PR 审查技能，大家一直在迭代（到现在还在改）。它会根据 PR 的性质启动不同的子智能体：一个管数据库集成安全，一个做复杂度分析标记冗余和过度设计，一个检查 prompt 健康度确保符合团队格式规范，另外还跑 linter 和 Ruff。

为什么在审查技能上投入这么多？**因为当智能体开始批量产出 PR 时，人工审查变成了瓶颈，而不是质量关卡。** Latent Space 有力地论证了代码审查正在走向死亡。自动化的、一致的、技能驱动的审查才是替代品。

MCP 这边，我用 Braintrust MCP 让 LLM 能查询评估日志并直接改东西；用 DeepWiki MCP 让智能体随时调取任何开源仓库的文档，不用手动拉进上下文。

当团队里好几个人在写同一个技能的不同版本时，**该整合成共享注册表了。** Block（节哀）写过一篇好文章：他们建了个内部技能市场，100 多个技能，按角色和团队打包推荐。技能跟代码享受同等待遇：Pull Request、审查、版本历史。

还有个趋势值得提：**LLM 越来越多地用 CLI 工具代替 MCP。**（好像每家公司都在发一个——Google Workspace CLI、Braintrust 也快了。）原因是 token 效率。MCP 服务器每一轮都把完整的工具定义塞进上下文，不管智能体用不用。CLI 反过来：智能体执行一条精准的命令，只有相关输出进入上下文窗口。我大量使用 agent-browser 而不是 Playwright MCP，就是这个原因。

继续之前要插一句。**Level 3 到 5 是后面一切的地基。** LLM 在某些事上出奇地好、在另一些事上出奇地差，你得先培养出对这些边界的直觉，再往上堆更多自动化。上下文嘈杂、prompt 模糊或有误导、工具描述写得糙，Level 6 到 8 只会把这些混乱成倍放大。

## Level 6：工程脚手架与自动反馈循环

![Harness Engineering](/images/reading/agentic-engineering-4.jpg)

**到这一步，火箭才真正点火升空。**

上下文工程管的是模型「看到」什么。工程脚手架管的是搭建整套环境、工具链和反馈循环，**让智能体不需要你盯着也能可靠地干活。给智能体的不该只是编辑器，而是一条完整的反馈回路。**

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航都接进了智能体运行环境。它能截屏、驱动 UI 路径、查日志、验证自己的修复。给一个 prompt，智能体就能复现 bug、录视频、写修复。然后它自己驱动应用做验证，提 PR，回应 review 意见，合并——**只有需要判断力的时候才交给人。** 智能体不只是写代码，它能看到代码跑出来的结果，然后迭代——跟人做的一模一样。

我的团队做的是技术故障排除的语音和聊天智能体，所以我写了一个叫 converse 的 CLI 工具，让任何 LLM 都能跟我们的后端端点逐轮对话。LLM 改完代码后用 converse 对着真实系统测试对话，再迭代。**有时候这些自我改进的循环会连续跑好几个小时。** 当结果可验证时尤其强大：对话必须走这个流程，或者在某些场景下必须调用特定工具（比如升级到人工客服）。

让这一切成为可能的核心概念叫**反压**（Backpressure，借自分布式系统，指系统内置的自动约束和纠错能力）：类型系统、测试、linter、pre-commit 钩子——**这些自动化反馈机制让智能体无需人工介入就能发现并修正错误。** 要自主性，就必须有反压。没有反压的自主，只会产出一堆垃圾。安全领域同理。Vercel 的 CTO 指出，智能体、它们生成的代码和你的密钥应该分处不同的信任域——因为日志文件里埋一条 prompt 注入攻击，就可能诱骗智能体泄露你的凭证（如果一切都跑在同一个安全上下文里的话）。**安全边界就是反压：它约束的不是智能体该做什么，而是它脱轨后能做什么。**

两条实用经验：

- **追求吞吐量，别追求完美。** 如果每次提交都要求零缺陷，智能体就会扎堆在同一个 bug 上、互相覆盖修复。不如容忍小的非阻塞问题，发布前做一次最终质量审查。我们对人类同事也是这么做的。

- **约束比指令更有用。** 按部就班的 prompting（「先做 A，再做 B，然后做 C」）越来越过时了。我的经验是，**划好边界比给一张清单管用得多**——智能体会死磕清单、忽略清单以外的一切。更好的 prompt 是：「这是我要的东西，做到所有测试通过为止。」

工程脚手架的另一半，是确保智能体在没你的情况下也能自己在代码仓库里找到方向。OpenAI 的做法：**AGENTS.md 控制在 100 行左右**，充当目录指向各处的结构化文档，并把文档的新鲜度纳入 CI 流程——不靠临时更新，那种东西一转眼就过时了。

这些都搭好之后，一个自然而然的问题就浮出水面了：智能体能验证自己的工作、能在仓库里导航、能在你不在的时候自我纠错——**那你为什么还得坐在电脑前？**

## Level 7：后台智能体

![Background Agents](/images/reading/agentic-engineering-5.jpg)

**大胆预判：计划模式正在走向消亡。**

Boris Cherny——Claude Code 的创造者——到今天还有 80% 的任务从计划模式开始。但每一代新模型，规划后一次通过的成功率都在攀升。**我认为我们正在逼近一个节点：计划模式作为一个独立的人工审批环节将逐渐消失。** 不是因为规划不重要了，而是模型自己规划的能力已经够好了。前提是：你在 Level 3 到 6 的功课做到位了。上下文干净、约束明确、工具描述清晰、反馈循环紧密，模型就能在不需要你签字的情况下可靠地规划。要是这些功课没做，你还是得盯着。

说清楚，规划本身不会消失，只是换了形态。对新手来说，计划模式仍然是正确的起点（如 Level 1 和 2 所述）。但到了 Level 7 面对复杂特性时，「规划」看起来不再像写一份分步大纲，而更像是**探索**：探测代码库、在工作树里原型化方案、勘测解决方案空间。而且越来越多时候，后台智能体在替你做这些探索。

这很关键，因为这正是解锁后台智能体的钥匙。**如果智能体能自己制定靠谱的计划并执行、不需要你点头，它就能在你干别的事时异步跑起来。** 这是从「我在手忙脚乱切标签页」到「活儿在没有我的情况下推进着」的质变。

Ralph 循环（以创建者 Ralph 命名的一种自主编码循环模式）是流行的入门方式：一个自主智能体不断运行编码 CLI，直到所有 PRD（产品需求文档）项目完成，每轮迭代都生成一个干净上下文的新实例。以我的经验，把 Ralph 循环跑对很难，PRD 里任何表述不清或有误导的地方都会反噬。它有点太「发射后不管」了。

你可以并行跑多个 Ralph 循环，但智能体越多，你就越发现自己的时间花在了哪里：协调它们、排优先级、检查输出、这边推一把那边戳一下。你已经不写代码了。**你变成了一个中层管理者。** 你需要一个编排智能体来处理调度，让你能专注于意图而非后勤。

我重度使用的工具是 Dispatch——我自己写的一个 Claude Code 技能，把你的会话变成指挥中心。你待在一个干净的主会话里，工人智能体在隔离的上下文中干重活。调度器负责规划、委派和追踪，你的主上下文窗口留给编排。**工人卡住的时候，它会浮上来问一个澄清问题，而不是默默失败。**

Dispatch 在本地运行，适合快速开发——反馈更即时、交互式调试更顺手、没有基础设施开销。Ramp 的 Inspect 是互补方案，适合更长期的自主任务：每个智能体会话在云端沙箱 VM 里启动，自带完整开发环境。PM 发现一个 UI bug，在 Slack 标记一下，Inspect 就接手跑起来——你的笔记本合上了也没关系。代价是运维复杂度（基础设施、快照、安全），换来的是本地智能体做不到的规模和可复现性。我的建议：两种都用。

**这个层级有一个出乎意料的强大打法：让不同的模型干不同的活儿。** 最好的工程团队不是由一群克隆人组成的——团队强，是因为每个人思维方式不同、经历不同、擅长的东西不同。LLM 也一样。这些模型经过不同的后训练，性格差异显著。我日常的做法是：Opus 做实现、Gemini 做探索性调研、Codex 做审查——**合力产出比任何单一模型单干都强。** 可以理解为群体智慧的代码版。

关键是，**实现者和审查者必须分开。** 这个亏我吃过太多次了：同一个模型实例既写代码又评估自己的工作，它是有偏见的。它会忽略问题、告诉你所有任务都完成了——其实没有。这不是恶意，跟你不能给自己的考试打分是一个道理。让不同的模型（或一个带审查专用 prompt 的不同实例）来做审查，信号质量会大幅提升。

后台智能体还**打开了 CI 与 AI 结合的大门**。智能体能在没人坐镇时自己跑了，就可以从现有基础设施触发它们：一个文档机器人在每次合并后重新生成文档、提 PR 更新 CLAUDE.md（我们在用，省了大量时间）；一个安全审查器扫描 PR 并提交修复；一个依赖机器人真正去升级包、跑测试套件，而不是只标记一下。好的上下文、复利规则、称手的工具、自动反馈循环——现在全部自主运转。

## Level 8：自主智能体团队

**还没有人站稳这一级**，但有几家在往里冲。这是活跃的前沿。

Level 7 是一个编排者 LLM 以中心辐射式向工人 LLM 派活。Level 8 把这个瓶颈拿掉了。**智能体之间直接协调**：认领任务、共享发现、标记依赖、解决冲突——不再需要所有事情都经过一个中央调度。

Claude Code 的实验性 Agent Teams 功能是早期实现：多个实例在共享代码库上并行工作，每个队友在自己的上下文窗口里运行，直接互相通信。Anthropic 用 16 个并行智能体从零构建了一个能编译 Linux 的 C 编译器。Cursor 用数百个并发智能体跑了好几周，从零构建了一个网页浏览器，并把自家代码库从 Solid 迁移到了 React。

但仔细看就能看到裂缝。Cursor 发现没有层级结构，智能体会变得畏手畏脚、原地打转。Anthropic 的智能体不断破坏已有功能，直到加了 CI 流水线防回归才好转。**每个在这一级做实验的人都说同一句话：多智能体协调是一个困难问题，没有人接近最优解。**

说实话，我不认为模型已经准备好了应对多数任务的这种自主程度。即便它们足够聪明，目前仍然太慢、太费 token，在「登月级」项目（编译器、浏览器构建——确实惊艳，但远谈不上干净）之外不划算。**我们多数人每天干的活儿，杠杆在 Level 7。** Level 8 最终可能成为主流模式我不会意外，但此刻我会把精力放在 Level 7（除非你是 Cursor——突破本身就是生意）。

## Level ?

绕不开的「下一步是什么」。

当你已经能利索地编排智能体团队，交互界面就没理由只停留在文本上。**语音对语音**（甚至思维对思维？）跟编码智能体交互——对话式的 Claude Code，而不只是语音转文字输入——是自然的下一步。看着你的应用，大声说出一连串修改，然后看着它们在眼前发生。

有一群人在追「完美一枪」：说出你要什么，AI 一次完美搞定。问题在于这预设了人类精确地知道自己想要什么。**我们不知道，从来就不知道。** 软件一直都是迭代的，我认为它永远会是。只是它会变得容易得多、远远超越纯文本交互、而且快得多。

那么：你在哪一级？你在做什么来到达下一级？
