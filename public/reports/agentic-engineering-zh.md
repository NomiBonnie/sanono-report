# 智能体工程的 8 个段位 — Bassim Eledath

> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个段位里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

---

AI 写代码的能力已经跑在我们前面了。这也是为什么 SWE-bench 跑分再怎么刷新纪录，工程负责人关心的那些生产力指标却没什么起色。Anthropic 团队用 10 天就做出了 Cowork，另一个团队拿着同样的模型连个 POC 都搞不定。区别在哪？一个团队把"模型能力"和"实际用法"之间的鸿沟填上了，另一个没有。

这个鸿沟不会一夜之间消失。它是一级一级填的。总共 8 级。读到这里的人大多已经过了前面几级，而你应该迫切地想往上走，因为每升一级，产出都是跨越式增长，而且模型每次进步都会进一步放大你在高等级获得的收益。

还有件事你可能没想到：你的效率不只取决于自己。假设你已经到了第 7 级，晚上睡觉的时候后台智能体在帮你提 PR。但代码仓库要求同事审批才能合并，而那个同事还停在第 2 级，手动审代码。你的吞吐量就这样被卡住了。所以帮队友升级这件事，直接关系到你自己的效率。

跟不少团队和个人聊下来，我观察到的进阶路径大致如下（不完全线性）：

## 第 1 和第 2 级：Tab 补全与 Agent IDE

这两级简单带过，主要是记录完整。可以快速跳过。

一切始于 Copilot 和 Tab 补全。按一下 Tab，代码自动补完。很多人可能早就忘了这个阶段，后来入行的人可能压根没经历过。这个阶段对老手更友好，他们能先搭好代码骨架，让 AI 填充细节。

Cursor 这类 AI IDE 改变了局面，把聊天接口和代码库直接打通，跨文件编辑变得容易很多。但天花板始终是上下文：模型只能帮到它能"看到"的部分，而且经常该看的没看到，不该看的塞了一堆。

在这个阶段，大多数人也开始尝试计划模式：把一个粗略想法转化成分步计划，反复迭代，然后启动执行。这在当前阶段很好用，是保持掌控感的合理方式。不过到了更高等级，对计划模式的依赖会逐渐减少。


![Context Engineering](/images/reading/agentic-engineering-3.jpg)

## 第 3 级：上下文工程

2025 年最火的概念之一。简单说，上下文工程就是"给 AI 看什么、不看什么"。模型终于能听话干活了，但有个前提：你喂给它的信息得刚刚好。给多了它晕，给少了它猜。所以大家开始琢磨怎么让每一条信息都物有所值。

实际操作中，上下文工程涉及的面很广。你写的规则文件是上下文工程，你怎么描述工具是上下文工程（AI 靠这些描述来决定用哪个工具），对话记录怎么管理也是（别让 AI 聊着聊着忘了自己在干什么），甚至每一轮给 AI 看几个工具也得讲究（选项太多它会懵，跟人一样）。

现在这个话题没那么火了，因为模型越来越扛噪音，能处理更长的对话了。但有几种场景还是会踩坑：

- **小模型更挑食。** 语音应用经常用小模型，喂的信息越多，响应越慢。

- **有些工具特别烧资源。** 比如浏览器自动化工具和图片输入，会让你的对话很快触到长度上限。

- **工具太多反而碍事。** AI 光是读工具说明就消耗大量资源，真正干活的时间反而少了。

总的来说，上下文工程没有过时，只是进化了。重心从"过滤无用信息"转向了"在对的时间给对的信息"。


![Compounding Engineering](/images/reading/agentic-engineering-4.jpg)

## 第 4 级：复利工程

上下文工程让当前会话变得更好。复利工程（Compounding Engineering）更厉害，它让之后的每一次会话都比上次强。Kieran Klaassen 把这个概念带火了，对我和很多人来说是一个转折点：原来凭感觉编程（Vibe Coding）不只是做原型用的。

核心是一个"计划、委派、评估、编码化"的循环。你规划任务，给 LLM 足够的上下文；把任务交出去；评估输出；然后最关键的一步，把学到的东西编码化：什么有用、什么出了问题、下次该遵循什么模式。

复利就复利在这一步。LLM 没有记忆。昨天引入了一个你明确删掉的依赖，明天它照犯不误，除非你写下来告诉它别这么做。最常见的做法是更新 CLAUDE.md（或同类规则文件），把教训固化到每次会话中。不过要注意：什么都往规则文件里塞反而会适得其反（指令太多等于没有指令）。更好的做法是创造一个环境，让 LLM 能自己找到有用的上下文，比如维护一个最新的 docs/ 文件夹（第 7 级会详细讲）。

习惯了复利工程的人，对喂给 LLM 的上下文特别敏感。LLM 犯了错，第一反应是"是不是上下文缺了什么"，而不是怪模型不行。有了这种直觉，后面几级才走得通。


![MCP and Skills](/images/reading/agentic-engineering-5.jpg)

## 第 5 级：MCP 与技能

第 3 和第 4 级搞定的是上下文。第 5 级搞定的是能力。MCP 和自定义技能让 LLM 能访问数据库、API、CI 流水线、设计系统，用 Playwright 做浏览器测试，用 Slack 发通知。模型不再只是看代码想方案，它能直接动手操作了。

关于 MCP 和技能的好文章已经不少了，这里不复述概念。说几个我的实际用法：我们团队共享一个 PR 审查技能，大家一起迭代（现在还在改），它会根据 PR 的性质有条件地启动子智能体。一个负责检查数据库集成的安全性，一个跑复杂度分析找冗余和过度工程，一个检查提示词是否符合团队标准格式，另外还会跑 linter 和 Ruff。

为什么在审查技能上投入这么多？因为智能体批量提 PR 之后，靠人审代码已经跟不上了。Latent Space（AI 领域知名媒体）有一个观点：传统的代码审查方式已经走到头了，取代它的是自动化审查。

MCP 方面，我用 Braintrust MCP 让 LLM 查询评估日志并直接做修改。用 DeepWiki MCP 让智能体访问任何开源仓库的文档，不用手动拉到上下文里。

当团队里多个人都在写同一个技能的不同版本时，就值得整合成共享仓库了。Block（原 Square，节哀）有一篇很好的文章讲这件事：他们建了一个内部技能市场，超过 100 个技能，还有针对不同角色和团队的技能套餐。技能和代码一样管理：PR、审查、版本历史。

LLM 越来越多地用命令行工具而不是 MCP。原因很简单：MCP 每次调用都会把所有工具的完整说明塞进对话，不管用不用得上，很浪费。命令行工具正好反过来：执行一个具体命令，只有结果进入对话。

继续往下之前说一件事。第 3 到第 5 级是后面所有等级的地基。LLM 擅长什么、不擅长什么有很多出人意料的地方，你需要先摸清这些边界，再往上堆自动化。上下文乱七八糟、提示词含糊不清、工具描述敷衍了事的话，第 6 到第 8 级只会把这些问题成倍放大。


![Harness Engineering](/images/reading/agentic-engineering-6.jpg)

## 第 6 级：工程脚手架与自动反馈环

到这一级，真正开始起飞了。

上下文工程管的是模型看到什么。工程脚手架（Harness Engineering）管的是模型干活的整个环境：工具链、反馈回路，目标是让智能体不需要你介入就能可靠地完成工作。核心理念：给智能体的不只是编辑器，而是完整的反馈环。

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航都接入了智能体运行时，能截屏、操作 UI、查日志、验证自己的修复。给一个提示词，智能体就能复现 bug、录制视频、实现修复，然后通过操作应用来验证，提 PR，回应审查意见，合并代码。只在需要人类判断的时候才上报。智能体不只是在写代码，它能看到代码跑起来的效果并迭代，跟人类开发者一样。

我的团队做的是技术故障排查的语音和聊天智能体，所以我做了一个叫 converse 的 CLI 工具，让任何 LLM 都能和我们的后端对话、进行多轮交互。LLM 改完代码，用 converse 对着线上系统跑对话测试，然后迭代。这种自我改进的循环有时候会连续跑好几个小时。当结果可以验证的时候特别好用：对话必须按这个流程走，或者在特定情况下调用特定工具（比如转接人工客服）。

为什么这套东西能跑起来？靠的是自动纠错机制：类型检查、测试、代码规范检查、提交前的自动校验。这些机制让 AI 能自己发现错误、自己改正，不用人盯着。想让 AI 自主干活，这些纠错机制必不可少。没有它们，产出一团糟。

安全方面也是同理。Vercel 的 CTO 提出一个重要原则：AI 智能体、它写的代码和你的密码密钥，应该隔离在不同的安全区域。为什么？因为一个藏在日志里的恶意指令就可能骗 AI 把你的密码偷走。安全隔离本身就是一种纠错机制：限制的是 AI 跑偏时"能做什么"。

两个实用建议：

- **追求吞吐量，而不是完美。** 如果要求每次提交都完美，多个智能体会在同一个 bug 上反复打转，互相覆盖对方的修复。不如容忍小的非阻塞性错误，发布前做一轮最终质量检查。我们对人类同事也是这么做的。

- **约束优于指令。** "先做 A，再做 B，再做 C"这种步骤式提示词越来越不好使了。根据我的经验，定义边界比给清单更有效，因为智能体会盯着清单，忽略清单上没有的东西。更好的提示是"这是我想要的结果，做到通过所有测试为止"。

工程脚手架的另一面是确保智能体能自己在代码仓库里找路。OpenAI 的做法：把 AGENTS.md 控制在大约 100 行，当作目录索引指向其他结构化文档，并且把文档新鲜度检查放进 CI，而不是靠随手更新（那种很快就会过时）。

所有这些都搭好之后，一个问题自然浮出来：如果智能体能自己验证工作、自己导航代码仓库、自己纠正错误，你为什么还要坐在电脑前？

## 第 7 级：后台智能体

大胆说一句：计划模式要过时了。

Claude Code 的创造者 Boris Cherny 今天仍然有 80% 的任务以计划模式开始。但每一代新模型出来，一次性成功的概率都在爬升。我觉得我们快到那个临界点了：计划模式作为独立的人类审批步骤会逐渐消失。不是因为计划本身不重要，而是模型自己规划的能力越来越强了。重要前提：只有在你做好了第 3 到第 6 级的工作之后才成立。上下文干净、约束明确、工具描述清楚、反馈环路完善，模型不需要你审查计划就能可靠执行。这些没做好，你还是得盯着。

澄清一下，规划这件事本身不会消失，只是形态在变。新手还是应该从计划模式入门。但到了第 7 级，"规划"不再是列大纲，而是探索：摸索代码库、做小实验、勘探不同方案。而且越来越多的时候，后台智能体在替你做这种探索。

这很关键，因为正是这一点解锁了后台智能体。如果智能体能自己定出靠谱的计划并执行，不需要你签字确认，它就能异步运行，你去做别的事。这才是从"我在切换多个标签页"到"有些工作在没我的情况下也在推进"的质变。

Ralph 循环是常见的入门方式：设定一个目标清单，让 AI 反复运行直到全部完成，每一轮都用干净的新实例。但根据我的经验，目标写得不够清楚就会翻车，有点太"放出去不管"了。

你可以并行跑多个 Ralph 循环，但智能体越多，你越会发现时间花在哪里：协调它们、排列任务顺序、检查输出、推一把卡住的。你已经不写代码了，你变成中层管理了。你需要一个编排智能体来分发任务，这样你才能专注于意图而不是后勤。

我最近重度使用的工具是 Dispatch，这是我自己做的一个 Claude Code 技能，能把你的会话变成指挥中心。你待在一个干净的主会话里，工作智能体在隔离的上下文中干活。调度器负责规划、分发和跟踪，你的主上下文窗口保留给编排。工作智能体卡住了会提出澄清问题，而不是默默失败。

Dispatch 跑在本地，适合快速开发：反馈更快、调试更方便、不需要基础设施。Ramp 的 Inspect 是互补方案，适合更长时间、更自主的工作：每个智能体会话在云端沙箱虚拟机中启动，带完整的开发环境。一个产品经理在 Slack 里标记了一个 UI bug，Inspect 接手，你合上笔记本电脑它也在跑。代价是运维复杂度（基础设施、快照、安全），但你得到的是本地智能体做不到的规模化和可复现性。我建议两种都用。

这个级别有一个出人意料的强力模式：给不同的任务用不同的模型。最好的工程团队不是由一群一模一样的人组成的，而是各有所长、思路各异的人。LLM 也一样。这些模型经过了不同的后训练，性格差异很大。我经常让 Opus 做实现、Gemini 做探索性研究、Codex 做审查，组合起来的产出比任何单个模型都强。代码版的群体智慧。

还有一点很关键：实现者和审查者必须分开。我在这上面吃过太多亏了。同一个模型实例既写代码又评估自己的工作，它一定会有偏见。会忽略问题，告诉你所有任务都完成了，其实并没有。这不是恶意，道理很简单：自己不能给自己判卷。让另一个模型（或者另一个带有审查专用提示词的实例）来做审查，信号质量会大幅提升。

后台智能体还打开了"AI + 自动化流水线"的大门。AI 能无人值守工作之后，就可以接入现有的自动化系统。比如：每次代码合并后自动重新生成文档、自动扫描安全问题并提交修复、自动升级依赖包并跑测试。前面几级积累的上下文管理、知识复利、工具能力、自动纠错，全都在这里发挥作用。

## 第 8 级：自主智能体团队

目前还没有人真正掌握这一级，但有几个团队正在探索。这是当下的前沿。

在第 7 级，你有一个编排 LLM 以中心辐射模式把任务分发给工作 LLM。第 8 级去掉了这个瓶颈。智能体之间直接协调：认领任务、共享发现、标记依赖关系、解决冲突，不再把所有东西都路由到一个中心节点。

Claude Code 实验性的 Agent Teams 功能是早期实现之一：多个实例在共享代码库上并行工作，每个队友有自己的上下文窗口，彼此直接通信。Anthropic 用 16 个并行智能体从零开始构建了一个能编译 Linux 的 C 编译器。Cursor 让数百个并发智能体跑了好几周，从零做了一个浏览器，还把自己的代码库从 Solid 迁移到了 React。

但凑近看就能看到缝隙。Cursor 发现没有层级管理的话，智能体会犹豫不决、原地打转。Anthropic 的智能体不断破坏已有功能，直到加上了自动化的回归测试。所有在这个级别实验的人都说同一句话：多智能体协调很难，离成熟还远着呢。

说实话，我不认为现在的模型撑得起这种自主水平。就算够聪明，速度慢、费用高，除了"从零造一个编译器"这种大型挑战项目（确实厉害，但离实用还远），日常工作划不来。对我们大多数人来说，第 7 级才是投入产出比最高的阶段。

## 第 ? 级

不可避免的"接下来是什么"问题。

当你能熟练编排智能体团队的时候，没理由非得停在打字界面。跟你的编程 AI 直接语音对话，不是语音转文字，而是真正的对话，这是自然的下一步。看着你的应用，大声描述一连串修改，然后看着它们在眼前发生。

有一群人在追求完美的一次成型：说出你想要什么，AI 一次生成完美结果。但这套逻辑有个根本问题：它假设我们人类清楚自己要什么。我们不清楚。从来就不清楚。软件一直是迭代着做出来的，我觉得永远都会是。只是以后会容易很多，会超越纯文字交互，而且快得多。

所以：你在哪一级？你打算怎么升到下一级？
