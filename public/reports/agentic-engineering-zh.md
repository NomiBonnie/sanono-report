# 智能体工程的 8 个段位 — Bassim Eledath

> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个段位里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

---

AI 写代码的能力，已经远远甩开了我们驾驭它的能力。这就是为什么 SWE-bench（AI 编码能力的标准测试基准）分数拼命往上刷，工程管理层真正看重的生产力指标却纹丝不动。Anthropic 团队 10 天就能把 Cowork 上线，另一个团队拿着一模一样的模型连个 POC（概念验证）都搞不定。区别就一个：一个团队把能力和实践之间的距离走通了，另一个没有。

这个距离不会一夜走完，得一级一级爬，总共 8 级。读到这里的你，多半已经过了前面几级。但别停，赶紧往上走。每升一级，产出都是量级跃升，而且模型每变强一分，这些增益还会被进一步放大。

还有件事可能出乎你意料：你的产出，比你想象中更依赖身边人的水平。打个比方，你已经到了第 7 级，晚上睡觉时后台智能体（Background Agents）就替你提了好几个漂亮的 PR。但代码库规定合并前要同事审批，偏偏这位同事还在第 2 级，一行行手动看代码。你的速度，就这样被死死卡住了。所以拉队友进阶，就是在帮自己提速。

跟不少团队和个人聊过之后，我总结出了这样一条进阶路径。不一定严格按这个顺序，但大致如此：

## 第 1 级和第 2 级：Tab 补全与智能体 IDE

![Levels 1 & 2](/images/reading/agentic-engineering-2.jpg)

这两级我快速带过，留个记录。可以跳着看。

起点是 Copilot 和 Tab 补全。按一下 Tab，代码自动补上。很多人大概早忘了，后来入行的可能压根没经历过。它对老手更友好：先把代码骨架搭好，AI 负责填肉。

Cursor 这类 AI 原生 IDE 改了游戏规则。它把对话接进了代码库，多文件编辑一下子顺畅了很多。但天花板一直没变：上下文。模型只能帮到它看得见的部分，偏偏它经常该看的没看到，不该看的看了一堆。

这个阶段的人通常也在试计划模式（Plan Mode）：把粗略想法整理成一步步的计划交给模型，反复迭代，然后执行。在这个阶段很管用，也是保持掌控感的好办法。不过到了后面几级，对计划模式的依赖会越来越少。

## 第 3 级：上下文工程

![Context Engineering](/images/reading/agentic-engineering-3.jpg)

2025 年的年度热词。上下文工程（Context Engineering）之所以成为一门学问，是因为模型终于能在合适的上下文量下，可靠地执行合理数量的指令了。太多噪音和信息不足一样糟，所以重点变成了提高每个 token 的信息密度。当时大家都在说："每个 token 都得争取自己的位置。"

实际操作中，上下文工程涉及的面比大多数人意识到的要广。它包括系统提示词和规则文件（.cursorrules、CLAUDE.md）；包括工具描述的写法，因为模型要读这些描述来决定调用哪个工具；包括管理对话历史，避免长时间运行的智能体十轮对话之后跑偏；还包括每一轮该暴露哪些工具，因为选项太多会让模型跟人一样不知所措。

现在这个词提得少了。模型越来越能扛噪音，在更混乱的情境中也能推理（更大的上下文窗口也帮了忙）。但注意上下文消耗依然很有意义，几个例子：

- 小模型对上下文更敏感。语音应用常用小模型，上下文大小还跟首 token 延迟直接挂钩。

- token 消耗大户。Playwright 之类的 MCP（Model Context Protocol，模型上下文协议）和图片输入会飞速消耗 token，在 Claude Code 里很快就会触发"压缩会话"状态。

- 工具太多的智能体。模型花在解析工具描述上的 token 比干正事还多。

往大了说，上下文工程没有过时，只是进化了。关注点从"过滤坏的上下文"转向了"在对的时间提供对的上下文"。这个转变，直接为第 4 级铺好了路。

## 第 4 级：复利工程

![Compounding Engineering](/images/reading/agentic-engineering-4.jpg)

上下文工程改善的是当前这一次会话。复利工程（Compounding Engineering）改善的是之后的每一次。这个概念由 Kieran Klaassen 推广开来，对我和很多人来说都是一个转折点：原来凭感觉编程（Vibe Coding）不只是拿来做原型的。

它是一个"计划→委派→评估→沉淀"的循环。你规划好任务，提供足够的上下文让模型成功完成。你把任务交出去。你评估产出。然后最关键的一步：把学到的东西沉淀下来。什么好使，什么出了问题，下次该遵循什么模式。

沉淀这一步才是"复利"的来源。大语言模型是无状态的。你昨天明确移除了一个依赖，它明天还会给你加回来，除非你告诉它别这么干。最常见的做法是更新 CLAUDE.md（或同类规则文件），让这条经验写进未来每次会话。不过得提醒一句：什么都往规则文件里塞会适得其反——指令太多等于没有指令。更好的做法是营造一个让模型能自己找到有用上下文的环境，比如维护一个时刻更新的 docs/ 文件夹（第 7 级会展开讲）。

实践复利工程的人通常对送进模型的上下文极其敏感。模型犯了错，他们的第一反应是"是不是上下文没给够"，而不是"模型不行"。有了这种直觉，后面几级才走得通。

## 第 5 级：MCP 与技能扩展

![MCP and Skills](/images/reading/agentic-engineering-5.jpg)

第 3 和第 4 级解决的是上下文问题。第 5 级解决的是能力问题。MCP 和自定义技能（Skills）让模型能访问你的数据库、API、CI 流水线、设计系统，用 Playwright 做浏览器测试，用 Slack 发通知。模型不再只是"想"你的代码，它能"动手"了。

MCP 和 Skills 的介绍文章已经不少，我就不重复了。说几个我自己的用法：我们团队共享一个 PR 审查技能，大家一直在迭代。它会根据 PR 的类型有条件地启动不同的子智能体。一个专门检查数据库集成安全，一个做复杂度分析找冗余和过度设计，一个检查提示词是否符合团队规范，另外还跑 linter 和 Ruff。

为什么在审查技能上投入这么多？因为智能体开始批量产出 PR 之后，人工审查就成了瓶颈，不再是质量关卡。Latent Space（一档科技播客）有个很有力的论点：传统意义上的代码审查已经死了，取而代之的是自动化、一致的、技能驱动的审查。

MCP 方面，我用 Braintrust MCP 让模型直接查询评估日志并做修改，用 DeepWiki MCP 让智能体随时调取任意开源仓库的文档，不用手动拉进上下文。

当团队里好几个人都在写同类技能的各自版本时，值得把它们合并成一个共享仓库。Block（就是以前的 Square，唉）有篇不错的文章讲这个：他们建了一个内部技能市场，100 多个技能，按角色和团队打包。技能的管理跟代码一样：PR、审查、版本历史。

还有个趋势值得留意：越来越多的模型开始用命令行工具替代 MCP（好像每家公司都在出一个：Google Workspace CLI、Braintrust 也快出了）。原因是 token 效率。MCP 服务器每一轮都把完整的工具描述注入上下文，不管智能体用不用得上。命令行工具反过来：智能体跑一条精准的命令，只有相关输出进入上下文窗口。我大量使用 agent-browser 而不是 Playwright MCP，就是这个原因。

接着往下走之前，有个重要前提。第 3 到第 5 级是后面一切的基石。大语言模型擅长什么、不擅长什么，分布很不均匀，你需要先摸出这些边界在哪里，才能在上面叠加更多自动化。如果你的上下文一团乱，提示词写得模糊或有偏差，工具描述不清楚，那第 6 到第 8 级只会把问题放大。

## 第 6 级：环境工程与自动反馈循环

![Harness Engineering](/images/reading/agentic-engineering-6.jpg)

到这一级，事情开始真正起飞。

上下文工程管的是模型看到什么。环境工程（Harness Engineering）管的是整套运行环境、工具链和反馈循环，让智能体不需要你干预就能可靠地完成工作。核心思路：给智能体的不只是编辑器，而是一整条反馈回路。

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航全接进了智能体运行时，让它能截图、走 UI 流程、查日志、验证自己的修复。给一句提示，智能体就能复现 bug、录屏、写修复代码。然后它自己驱动应用验证，开 PR，回应审查意见，合并代码。只有需要人类判断力的时候才上报。智能体不只是写代码，它能看到代码跑出来的效果，然后迭代改进，跟人做的一模一样。

我们团队做语音和聊天 AI 客服，所以我写了一个命令行工具叫 converse，让任何大语言模型都能跟我们后端端点对话，进行多轮会话。模型改完代码，用 converse 对线上系统跑测试对话，然后迭代。这种自我改进循环有时一跑就是好几个小时。当结果可验证时尤其强力：对话必须走这条流程，或者在特定情况下调用特定工具（比如转人工）。

支撑这一切的核心概念是反压机制（Backpressure）：类型系统、测试、linter、pre-commit hook 这些自动反馈手段，让智能体不需要人就能发现并修正错误。想要自主性，就得有反压。不然出来的就是一台垃圾制造机。安全方面也一样。Vercel 的 CTO 主张智能体、它生成的代码和你的密钥应该放在不同的信任域（Trust Domains）里，因为一条藏在日志文件里的提示词注入就可能诱使智能体偷走你的凭证——前提是所有东西共享同一个安全上下文。安全边界本质上也是反压：它约束的不只是智能体"应该"做什么，更是它"脱轨时能做什么"。

两条实用经验：

- **追求吞吐量，不追求完美。** 如果每次提交都要求完美，智能体会在同一个 bug 上反复纠缠，互相覆盖修复。更好的做法是容忍小的、不阻塞的问题，发布前做一次统一的质量检查。对人类同事我们也是这么做的。

- **约束比指令管用。** 一步步告诉模型"先做 A，再做 B，再做 C"的方式正在过时。我的经验是，定义边界比给清单更好用，因为模型会盯着清单上的项目做，清单之外的全都忽略。更好的提示方式是："这是我要的东西，做到通过所有测试为止。"

环境工程的另一半是确保智能体在你的代码库里能自己找到路。OpenAI 的做法是：AGENTS.md 控制在 100 行左右，当作目录，指向其他地方的详细文档；文档的时效性交给 CI 来保证，不靠临时的人工更新。

当这些都搭建完之后，一个自然的问题浮出来了：如果智能体能自己验证工作、自己导航代码库、自己纠错，你为什么还需要坐在那里？

## 第 7 级：后台智能体

![Background Agents](/images/reading/agentic-engineering-7.jpg)

大胆说一句：计划模式正在走向消亡。

Boris Cherny，Claude Code 的创造者，今天依然有 80% 的任务从计划模式开始。但每一代新模型出来，规划后的一次成功率都在攀升。我觉得我们正在接近一个临界点：计划模式作为一个需要人参与的独立步骤，即将淡出。不是说规划不重要，而是模型自己规划的能力已经足够好了。但有个大前提：你得在第 3 到第 6 级做好功课。上下文干净、约束明确、工具描述清晰、反馈循环紧密，模型才能在你不审的情况下可靠地规划。如果这些没做好，你还是得盯着计划看。

澄清一下，规划本身不会消失，只是换了形态。对新手来说，计划模式仍然是最好的入口（如第 1 和第 2 级所述）。但到了第 7 级，面对复杂功能时，"规划"不再是写一步步的大纲，而更像是探索：查看代码库、在 worktree 里做原型、摸清方案空间。而且越来越多时候，后台智能体替你完成了这些探索。

这一点很关键，因为它恰恰是后台智能体得以成立的前提。如果智能体能自己做出靠谱的计划并执行，不需要你签字，它就可以在后台异步运行，你去干别的。这才是质变：从"我同时盯着好几个标签页"变成"有些工作在我不在的时候也在推进"。

Ralph 循环是常见的入门方式：一个自主循环反复运行编码 CLI，直到 PRD 上的所有项目完成，每轮迭代启动一个全新的干净实例。我的经验是，Ralph 循环很难调好，PRD 里任何含糊或缺失都会反噬。有点太甩手不管了。

你可以并行跑多个 Ralph 循环，但智能体开得越多，你越会发现自己的时间花在了哪里：协调它们、安排顺序、检查产出、推一把。你已经不写代码了，你变成了中层管理。你需要一个调度智能体来处理分配，好让自己专注于意图，而不是后勤。

我一直在重度使用的工具是 Dispatch，一个我自己写的 Claude Code 技能，把你的 session 变成指挥中心。你留在一个干净的 session 里，工人智能体在各自隔离的上下文中干活。调度器负责规划、分配、追踪，你的主上下文窗口留给编排。工人卡住了，它会抛出一个澄清问题，而不是悄悄失败。

Dispatch 跑在本地，适合需要紧盯进度的快速开发：反馈更快，调试更方便，没有基础设施开销。Ramp 的 Inspect 是互补方案，适合运行时间更长、更自主的工作：每个智能体 session 在云端沙箱 VM 里启动，带完整开发环境。PM 在 Slack 里提了个 UI bug，Inspect 接手就跑，你笔记本合上也没关系。代价是运维复杂度（基础设施、快照、安全），但换来的是本地智能体做不到的规模和可复现性。我的建议是两种都用。

这个阶段有个出人意料的有效模式：不同的任务用不同的模型。最强的工程团队不是一群克隆人，而是一群思维方式不同、训练背景不同、各有所长的人。大语言模型也一样。这些模型的后训练路径不同，性格气质差异明显。我日常的分工是：Opus 做实现，Gemini 做探索性调研，Codex 做审查。综合产出比任何单个模型独立工作都强。想想群体智慧，只不过用在了代码上。

还有一点很关键：实现者和审查者必须分开。我吃过太多次亏：同一个模型实例自己写代码又自己审查，它是有偏见的。它会掩盖问题，告诉你所有任务都完成了，其实并没有。这不是恶意，道理跟自己不能批自己的卷子一样。换一个模型（或者换一个带审查专用提示词的实例）来做审查，信号质量会大幅提升。

后台智能体还打开了 CI 与 AI 结合的大门。智能体既然不需要人坐在那里就能运行，那就把它们接进现有的基础设施。一个文档机器人，每次合并后自动重新生成文档，提一个 PR 更新 CLAUDE.md（我们在用，省了大量时间）。一个安全审查器，扫描 PR 并自动提修复。一个依赖升级机器人，不只是标记过期的包，而是真的升级并跑测试。好的上下文、复利化的规则、强大的工具、自动反馈循环，现在全部在自主运行。

## 第 8 级：自主智能体团队

![Autonomous Agent Teams](/images/reading/agentic-engineering-8.jpg)

还没有人真正掌握这一级，但有几个团队已经在往这个方向探索。这是当前的前沿。

第 7 级里，你有一个调度模型把任务分配给工人模型，中心辐射结构。第 8 级要去掉这个瓶颈。智能体之间直接协调：认领任务、共享发现、标记依赖、解决冲突，不再凡事都经过一个中心调度。

Claude Code 实验性的 Agent Teams 功能是一个早期实现：多个实例在共享代码库上并行工作，队友各有独立的上下文窗口，直接互相沟通。Anthropic 用 16 个并行智能体从零构建了一个能编译 Linux 的 C 编译器。Cursor 让数百个并发智能体跑了好几周，从零构建了一个浏览器，还把自己的代码库从 Solid 迁移到了 React。

但仔细看，破绽很明显。Cursor 发现没有层级结构时，智能体变得畏手畏脚，原地打转。Anthropic 的智能体不停破坏已有功能，直到加了 CI 流水线才止住退化。所有在这一级做实验的人都说同一句话：多智能体协调是个难题，离最优解还远着。

说实话，我觉得模型还没为大多数任务准备好这种程度的自主性。就算它们够聪明了，速度太慢、token 消耗太高，在编译器和浏览器这类登月项目之外不划算（让人印象深刻，但远谈不上干净利落）。对我们大多数人日常做的工作来说，第 7 级才是杠杆所在。第 8 级最终或许会成为主流模式，但现阶段我会把精力放在第 7 级（除非你是 Cursor，技术突破本身就是生意）。

## 下一步呢？

绕不开的问题：接下来是什么？

当你能顺畅地编排智能体团队，交互方式没必要停留在文字上。语音对话式编程——跟编码智能体直接对话的 Claude Code，不只是语音转文字输入——是自然的下一步。看着你的应用，大声说出一连串修改，然后看着它们在眼前发生。

有一群人在追求完美的一次成型：说出你要什么，AI 一次就写对。问题在于，这个前提假设我们人类清楚自己要什么。但我们从来都不清楚。软件开发从来都是迭代的，我相信它永远会是。只不过它会变得容易很多，远远超出纯文字交互，而且快得多。

那么：你在哪一级？你在做什么来到达下一级？
