# 智能体工程的 8 个段位 — Bassim Eledath

> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个段位里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

---

![The 8 Levels of Agentic Engineering](/sanono-report/images/reading/agentic-engineering-1.jpg)

AI 的编码能力，已经远远跑在了我们驾驭它的能力前面。这就是为什么 SWE-bench（SWE-bench，AI 编码能力的标准测试基准）分数刷得再高，工程管理层真正在意的生产力指标却没什么起色。Anthropic 团队能在 10 天内发布 Cowork 这样的产品，另一个团队用同样的模型却连一个 POC 都跑不通——区别在于，一个团队弥合了能力与实践之间的鸿沟，另一个没有。

这道鸿沟不会一夜之间消失。它是一级一级跨越的，一共 8 级。读到这里的大多数人可能已经过了前几级，而你应该迫不及待地冲向下一级——因为每往上一级，产出都是指数级跃升，模型能力的每次提升又会进一步放大这些增益。

你该在意的另一个原因是多人效应。你的产出比你以为的更依赖队友的段位。假设你是个 7 级高手，夜里让后台智能体（Background Agents）跑着就能产出好几个扎实的 PR。但如果你的代码库要求某个同事审批才能合并，而这位同事还停在第 2 级，手动审代码——你的吞吐量就被卡死了。所以拉高队友的段位，就是在帮你自己。

通过和很多实践 AI 辅助编程的团队和个人交流，我总结出了这样一条进阶路径，虽然不完全线性：

## 第 1 和第 2 级：Tab 补全与智能体 IDE

![Tab补全到智能体IDE](/sanono-report/images/reading/agentic-engineering-2.jpg)

这两级我快速带过，主要是为了记录完整。随意跳读。

一切始于 Copilot 和 Tab 补全。按下 Tab，自动补全代码。很多人大概早就忘了这回事，而后来入场的人可能压根没经历过。它更适合有经验的开发者——先把代码骨架搭好，再让 AI 填充细节。

以 Cursor 为代表的 AI 原生 IDE 改变了游戏规则，它把对话连接到了你的代码库，让多文件编辑变得轻松很多。但天花板始终是上下文。模型只能帮到它看得到的部分，而烦人的是，它经常要么没看到关键上下文，要么看了一堆没用的。

这个阶段的大多数人也在尝试自己用的编码智能体里的计划模式（Plan Mode）：把一个粗略想法转化为结构化的分步计划给 LLM，反复迭代，然后触发执行。在这个阶段确实好用，也是保持掌控感的合理方式。不过后面我们会看到，越往高段位走，对计划模式的依赖反而越少。

## 第 3 级：上下文工程

![上下文工程](/sanono-report/images/reading/agentic-engineering-3.jpg)

2025 年的年度热词，上下文工程（Context Engineering）之所以成为一个概念，是因为模型终于能稳定地在合适的上下文量下执行合理数量的指令了。嘈杂的上下文和不充分的上下文一样糟糕，所以核心工作就是提升每个 token 的信息密度。"每个 token 都得为自己在 prompt 里的位置拼命"——这就是当时的信条。

实际操作中，上下文工程涉及的面比大多数人意识到的要广。它包括你的系统提示词和规则文件（.cursorrules、CLAUDE.md）；包括你如何描述工具——因为模型会读这些描述来决定调用哪个；包括管理对话历史，让长时间运行的智能体不会在十几轮对话后跑偏；还包括决定每一轮暴露哪些工具——选项太多会让模型不知所措，就像人一样。

现在你已经不太听到"上下文工程"这个说法了。天平已经倾向了那些能容忍更嘈杂上下文、在更混乱的地形中推理的模型（更大的上下文窗口也帮了忙）。但注意上下文的消耗依然重要。举几个仍然会踩坑的例子：

- 小模型对上下文更敏感。语音应用经常用小模型，上下文大小还会影响首 token 延迟，直接关系到响应速度。

- 重 token 的工具和模态。Playwright MCP 和图像输入消耗 token 极快，会让你在 Claude Code 中比预期更早进入精简会话（Compact session，Claude Code 中上下文过长时自动触发的精简会话状态）。

- 接入了几十个工具的智能体，模型花在解析工具 schema 上的 token 比干正事还多。

更宏观地说，上下文工程并没有消失，只是进化了。重心从过滤掉坏的上下文，转移到确保正确的上下文在正确的时机出现。这个转变，正是第 4 级的铺垫。

## 第 4 级：复利工程

![复利工程](/sanono-report/images/reading/agentic-engineering-4.jpg)

上下文工程改善的是当前会话。复利工程（Compounding Engineering，类似复利效应——每一次改进都会累积到下一次，像利滚利一样越滚越大）改善的是之后的每一次会话。这个概念由 Kieran Klaassen 推广开来，它是一个转折点——不仅对我，也对很多人来说——让大家意识到凭感觉编程（Vibe Coding）远不止能做做原型。

这是一个"计划—委派—评估—沉淀"的循环。你为任务规划好足够的上下文让 LLM 能成功完成；你委派执行；你评估产出；然后，关键来了，你把学到的东西沉淀下来：什么好使了，什么崩了，下次该遵循什么模式。

正是"沉淀"这一步让它产生复利。LLM 是无状态的。如果它昨天重新引入了一个你明确删掉的依赖，明天它还会这么干——除非你告诉它不要。最常见的做法就是更新你的 CLAUDE.md（或等效的规则文件），把这些教训固化到每个未来的会话中。但要注意：把什么都往规则文件里塞的冲动可能适得其反——指令太多等于没有指令。更好的做法是创建一个环境，让 LLM 能自己方便地发现有用的上下文，比如维护一个时刻更新的 docs/ 文件夹（第 7 级会详细说）。

复利工程的实践者通常对输入给 LLM 的上下文极度敏感。当 LLM 犯错时，他们的第一反应是想"是不是少了什么上下文"，而不是怪模型能力不行。正是这种直觉，让第 5 到第 8 级成为可能。

## 第 5 级：MCP 与技能

![MCP与技能](/sanono-report/images/reading/agentic-engineering-5.jpg)

第 3 和第 4 级解决的是上下文问题。第 5 级解决的是能力问题。MCP（Model Context Protocol，模型上下文协议——一种让 AI 调用外部工具的标准协议）和自定义技能（Skills）让你的 LLM 能访问数据库、API、CI 流水线、设计系统，能用 Playwright 做浏览器测试，能用 Slack 发通知。模型不再只是"思考"你的代码库，它现在能直接"操作"它。

关于 MCP 和技能的好材料已经不少了，我就不重复介绍它们是什么。说说我怎么用的：我们团队共享了一个 PR 审查技能，大家一直在迭代（现在还是），它会根据 PR 的性质有条件地启动子智能体（Subagent）。一个负责检查与数据库的集成安全，一个做复杂度分析、标记冗余或过度工程，一个检查 prompt 健康度、确保我们的 prompt 符合团队标准格式。它还会跑 linter 和 Ruff。

为什么在审查技能上投入这么多？因为当智能体开始批量产出 PR，人工审查就变成了瓶颈，而不是质量关卡。Latent Space 有一个很有说服力的观点：我们熟悉的代码审查已经死了，取而代之的是自动化的、一致的、技能驱动的审查。

MCP 这边，我用 Braintrust MCP 让 LLM 直接查询评估日志并做出修改。我用 DeepWiki MCP 让智能体能访问任何开源仓库的文档，不需要手动拉进上下文。

当团队里多个人开始各自写同一个技能的不同版本时，就值得统一到一个共享仓库了。Block（节哀）有一篇很好的总结：他们建了一个内部技能市场，100 多个技能，还有按角色和团队策划的工具包。技能和代码享受同等待遇：Pull Request、审查、版本历史。

还有一个趋势值得说：LLM 越来越多地用 CLI 工具而不是 MCP（好像每家公司都在出一个：Google Workspace CLI、Braintrust 也快出了）。原因是 token 效率。MCP 服务器每轮都把完整的工具 schema 注入上下文，不管智能体用不用。CLI 反过来：智能体执行一条精准的命令，只有相关输出进入上下文窗口。我就是因为这个原因重度使用 agent-browser 而不是 Playwright MCP。

继续之前说一件事。第 3 到第 5 级是后面所有段位的基石。LLM 在某些事上好得出乎意料，在另一些事上又差得离谱，你需要在堆更多自动化之前，先培养出对这些边界的直觉。如果你的上下文嘈杂、prompt 描述不足或有误、工具描述潦草，第 6 到第 8 级只会把问题放大。

## 第 6 级：工程脚手架与自动反馈循环

![工程脚手架与反压](/sanono-report/images/reading/agentic-engineering-6.jpg)

到这里，火箭才真正点火升空。

上下文工程是策划模型看到什么。工程脚手架（Harness Engineering）是构建整个环境、工具链和反馈循环，让智能体能在你不介入的情况下可靠地完成工作。给智能体的不只是编辑器，而是整个反馈回路。

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航都接入了智能体运行时，让它能截图、驱动 UI 操作、查询日志、验证自己的修复。只需一条提示，智能体就能复现 bug、录制视频、实现修复，然后通过驱动应用来验证，提交 PR，回应审查反馈并合并——只在需要人类判断时才上报。智能体不只是写代码，它能看到代码跑出来的效果并迭代，和人类开发者一模一样。

我们团队做的是技术问题排查的语音和聊天智能体，所以我写了一个叫 converse 的 CLI 工具，让任何 LLM 都能和我们的后端接口聊天、逐轮对话。LLM 改完代码后，用 converse 对着真实系统测试对话，然后迭代。这些自我改进的循环有时候能连续跑好几个小时。当结果可验证时特别有效：对话必须走这条流程，或者在特定场景下调用特定工具（比如转人工）。

支撑这一切的核心概念是反压（Backpressure，源自分布式系统，指系统内置的自动约束和纠错能力）：类型系统、测试、linter、pre-commit hook 这些自动反馈机制，让智能体无需人工干预就能发现和纠正错误。要自主性，就必须有反压。否则你得到的只是一台垃圾生产机器。这也延伸到安全领域。Vercel 的 CTO 指出，智能体、它生成的代码、以及你的密钥应该放在不同的信任域中——因为一条埋在日志文件里的 prompt 注入，就可能骗智能体把你的凭证外泄，如果一切都在同一个安全上下文里的话。安全边界就是反压：它约束的是智能体失控时能做什么，而不仅仅是它应该做什么。

两个有用的原则：

- **为吞吐量设计，而不是为完美设计。** 如果要求每次提交都完美无缺，智能体会扎堆在同一个 bug 上，互相覆盖修复。不如容忍一些不阻塞的小问题，在发布前做一次最终质量检查。我们对人类同事也是这么做的。

- **约束 > 指令。** 一步一步的 prompt（"先做 A，再做 B，再做 C"）越来越过时了。以我的经验，定义边界比给清单更有效——因为智能体会死盯着清单，清单上没有的一概忽略。更好的 prompt 是"这是我想要的，干到所有测试通过为止"。

工程脚手架的另一半是确保智能体能在没有你的情况下理解你的代码库。OpenAI 的做法是：把 AGENTS.md 控制在 100 行左右，作为目录索引指向其他结构化文档，同时把文档的时效性纳入 CI 检查，而不是依赖容易过期的临时更新。

当你把这一切都搭建好之后，一个自然的问题就出现了：如果智能体能自己验证工作、理解代码库、在没有你的情况下纠正错误——你为什么还要坐在椅子上？

## 第 7 级：后台智能体

![后台智能体](/sanono-report/images/reading/agentic-engineering-7.jpg)

一个大胆的观点：计划模式正在消亡。

Claude Code 的创造者 Boris Cherny 至今仍有 80% 的任务从计划模式开始。但随着每一代新模型的出现，规划后的一次通过成功率在持续攀升。我认为我们正在接近一个节点：计划模式作为一个需要人类参与的独立步骤将逐渐淡出。不是因为规划不重要，而是模型已经越来越擅长自己规划了。但有一个大前提：只有你在第 3 到第 6 级做足了功课，这才成立。如果你的上下文干净、约束明确、工具描述完善、反馈循环紧密，模型就能可靠地自主规划，不需要你先过目。如果这些工作没做好，你还是得盯着计划。

说清楚：规划本身作为一种实践不会消失，只是在变形。对于新手，计划模式仍然是正确的入口（如第 1 和第 2 级所述）。但到了第 7 级的复杂功能开发，"规划"看起来不再像写一份分步大纲，而更像探索：探查代码库、在工作树（Worktree）中做原型实验、摸清解决方案的空间。而且越来越多时候，后台智能体在替你做这些探索。

这很重要，因为这正是后台智能体得以成立的关键。如果智能体能生成靠谱的计划并独立执行，不需要你签字确认，它就能异步运行——而你去做别的事。这是从"我在切换多个标签页"到"有些工作在自动进行"的质变。

Ralph 循环（Ralph Loop，以创建者 Ralph 命名的一种自主编码循环模式）是常见的入门方式：一个自主智能体循环，反复运行编码 CLI 直到 PRD（PRD，产品需求文档）中的所有条目完成，每次迭代都启动一个全新实例、带着干净的上下文。以我的经验，把 Ralph 循环调好很难，PRD 中任何描述不足或有误的地方都会反噬。它有点太"发射后不管（Fire-and-forget）"了。

你可以并行跑多个 Ralph 循环，但智能体越多，你越会发现时间其实花在了哪里：协调它们、安排顺序、检查产出、推一推卡住的。你不再写代码了——你变成了一个中层管理者。你需要一个编排智能体来处理调度，让你专注于意图而不是后勤。

我一直在重度使用的工具是 Dispatch，一个我写的 Claude Code 技能，它把你的会话变成一个指挥中心。你待在一个干净的主会话里，工作者在隔离的上下文中干活。调度器负责规划、委派和跟踪，你的主上下文窗口得以保留给编排。当某个工作者卡住时，它会抛出一个澄清问题，而不是默默失败。

Dispatch 在本地运行，特别适合需要贴近代码的快速开发：反馈更快、调试更方便、零基础设施开销。Ramp 的 Inspect 是互补方案，适合更长周期、更自主的工作：每个智能体会话在云端沙箱虚拟机里启动，配备完整的开发环境。PM 发现一个 UI bug，在 Slack 里标记一下，Inspect 就会接手处理——哪怕你的笔记本已经合上了。代价是运维复杂度（基础设施、快照、安全），但你换来的是本地智能体无法匹敌的规模化和可复现性。我的建议是两者都用（本地和云端后台智能体）。

这个级别有一个出人意料的强力模式：对不同任务用不同模型。最好的工程团队不是一群克隆人，而是一群思维方式不同、训练背景不同、各有所长的人。LLM 也是同理。这些模型的后训练方式不同，性格倾向也有显著差异。我日常让 Opus 做实现，Gemini 做探索性研究，Codex 做审查——综合产出比任何单一模型独自工作都强。群体智慧的代码版。

至关重要的是，你还必须把实现者和审查者分开。这个教训我交过太多次学费：如果同一个模型实例既实现又评估自己的工作，它会有偏见。它会掩盖问题，告诉你所有任务都完成了——实际上并没有。这不是恶意，原因和你不能给自己的考试打分一模一样。让不同的模型（或者带有审查专用 prompt 的不同实例）来做审查，你的信号质量会大幅提升。

后台智能体还打开了 AI 与 CI 结合的大门。一旦智能体能在无人值守的情况下运行，就可以从现有基础设施触发它们。一个文档机器人在每次合并后重新生成文档，并提 PR 更新 CLAUDE.md（我们就这么干的，省了大量时间）。一个安全审查器扫描 PR 并提交修复。一个依赖更新机器人真正去升级包并跑测试套件，而不是只标记一下。好的上下文、持续沉淀的规则、称手的工具、自动化的反馈循环——现在全都能自主运行了。

## 第 8 级：自主智能体团队

![自主智能体团队](/sanono-report/images/reading/agentic-engineering-8.jpg)

还没有人精通这一级，不过有些团队正在探索。这是当前的前沿。

在第 7 级，你有一个编排 LLM 以中心辐射式（Hub-and-spoke）模式向工作者 LLM 分发任务。第 8 级去掉了这个瓶颈。智能体之间直接协调——认领任务、共享发现、标记依赖、解决冲突——不再把一切都路由给一个中心编排器。

Claude Code 的实验性 Agent Teams（Claude Code 的实验性多智能体协作功能）是一个早期实现：多个实例在共享代码库上并行工作，每个队友在自己的上下文窗口中运作，彼此直接通信。Anthropic 用 16 个并行智能体从零构建了一个能编译 Linux 的 C 编译器。Cursor 让数百个并发智能体连续跑了几周，从零构建了一个 Web 浏览器，还把自家代码库从 Solid 迁移到了 React。

但仔细看就能发现缝隙。Cursor 发现没有层级结构时，智能体会变得畏首畏尾，原地打转毫无进展。Anthropic 的智能体不断破坏已有功能，直到加了 CI 流水线来防止回归。所有在这个级别实验的人都说同一句话：多智能体协调是一个极难的问题，没有人接近最优解。

说实话，我不认为模型在大多数任务上已经准备好了这种程度的自主性。就算它们足够聪明，速度仍然太慢、token 消耗太大，除了编译器和浏览器这类登月级项目（impressive，但远谈不上干净利落），在经济性上并不划算。对于我们大多数人的日常工作，第 7 级才是杠杆所在。第 8 级最终可能会成为主流模式，但现在我会把精力放在第 7 级（除非你是 Cursor，突破本身就是生意）。

## 第 ? 级

不可避免的"下一步是什么"。

一旦你能熟练编排智能体团队、摩擦降到最低，接口就没必要局限在纯文本了。语音对语音（思维对思维？或许？）与你的编码智能体交互——对话式的 Claude Code，而不只是语音转文字输入——是自然的下一步。看着你的应用，大声描述一连串修改，然后看着它们在眼前发生。

有一群人在追求完美的一次通过：说出你想要的，AI 一把就完美搞定。问题在于这预设了我们人类清楚地知道自己想要什么。我们不知道。从来都不知道。软件开发从来都是迭代的，我相信永远都会是。只不过它会变得容易得多，远远超越纯文本交互，而且快得多。

所以——你现在在哪一级？你在做什么来到达下一级？
