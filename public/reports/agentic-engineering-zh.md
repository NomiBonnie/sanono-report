>
> 对设计师和产品经理来说，这篇文章不是「程序员的事」。它描绘的是 **AI 协作的通用演化路径**：从单点工具（Level 1-2）到上下文管理（Level 3）到知识复利（Level 4）再到自主运行（Level 6-8）。你在用 AI 做设计、写文档、管理项目时，走的是同一条路。理解这 8 级，就能看清自己在哪一级、下一级需要什么、以及为什么有人用 AI 能 10 倍效率而你还在手忙脚乱。
>
> 文章最刺痛人的洞察是：**「你的产出比你想象的更依赖队友的水平。」** 你是 Level 7 大神，后台智能体睡觉时帮你提 PR——但如果你的同事还在 Level 2 手动 review 代码，你的吞吐量就被卡死了。这不是工具问题，是协作问题。AI 时代的团队效率，取决于最慢的那个人。所以别只顾着自己升级——拉队友上车，才是真正的杠杆。

# 智能体工程的 8 个层级

![The 8 Levels of Agentic Engineering](/images/reading/agentic-engineering-1.jpg)

**AI 的编码能力已经远远跑在了我们驾驭它的能力前面。** 这就是为什么 SWE-bench 跑分刷到飞起，却和工程管理层真正关心的生产力指标对不上号。Anthropic 的团队用 10 天就把 Cowork 这样的产品发布了，而另一个团队用着同样的模型，连一个 POC 都跑不通——**区别在于，一个团队弥合了能力与实践之间的鸿沟，另一个没有。**

这条鸿沟不会一夜之间消失。它是分层级跨越的——一共 8 个层级。读到这里的大部分人可能已经过了前几级，**你应该迫不及待地想到达下一级，因为每升一级，产出都是一次巨大的跃升**，而模型能力的每一次提升都会进一步放大这些收益。

你需要关心这件事的另一个原因是**多人协作效应**。你的产出比你想象的更依赖队友的水平。假设你是个 Level 7 大神，睡觉的时候后台智能体就帮你提了好几个靠谱的 PR。但如果你的仓库需要同事 review 才能合并，而这位同事还在 Level 2 手动审代码——你的吞吐量就被卡死了。**所以，拉队友升级，就是在帮自己。**

通过和多个团队和个人交流 AI 辅助编码的实践经验，以下是我观察到的层级演进路径（并不严格线性）：

## Level 1 & 2：自动补全与 Agent IDE

这两级我快速过一下，主要是为了记录完整性。可以随意跳过。

一切始于 Copilot 和 Tab 补全。按下 Tab 键，代码自动补完。很多人可能已经忘了这个阶段，而后来入场的人直接跳过了。**它对有经验的开发者更友好**——你得先把代码骨架搭好，AI 才能帮你填空。

以 Cursor 为代表的 AI IDE 改变了游戏规则，它把聊天窗口直接连到了你的代码库，**让跨文件编辑变得容易了一个数量级**。但天花板始终是上下文（Context）。模型只能帮到它能"看到"的部分，而令人抓狂的是，它要么没看到关键的上下文，要么看了一堆没用的。

在这个层级，大多数人也在尝试所用编码智能体的「计划模式」（Plan Mode）：把一个粗略的想法翻译成结构化的分步计划给 LLM，反复迭代计划，然后触发执行。在这个阶段这套方法挺好用，也是维持掌控感的合理方式。不过后面几级会越来越少依赖计划模式。

## Level 3：上下文工程（Context Engineering）

![Context Engineering](/images/reading/agentic-engineering-2.jpg)

上下文工程是 2025 年的年度热词。当模型开始能够可靠地在适量上下文下执行合理数量的指令时，这个概念就立住了。**嘈杂的上下文和不充分的上下文一样糟糕**，所以核心功夫在于提升每个 token 的信息密度。当时的口号是：「每个 token 都得为自己在 prompt 中的位置而战。」

在实践中，上下文工程涉及的面比大多数人意识到的要广。它包括你的系统提示和规则文件（.cursorrules、CLAUDE.md）；包括你如何描述工具——因为模型是读工具描述来决定调用哪个的；包括管理对话历史，让长时间运行的智能体不会在第十轮对话后就跑偏；还包括决定每一轮暴露哪些工具——**太多选项会让模型蒙圈，就像选项太多会让人蒙圈一样。**

现在你听到上下文工程的频率没那么高了。天平已经倾向于那些能容忍更嘈杂上下文、在更混乱的场景中推理的模型（更大的上下文窗口也有帮助）。但注意什么在吃上下文，仍然很重要。几个还会踩坑的场景：

- **小模型对上下文更敏感。** 语音应用通常用小模型，上下文大小还和首个 token 的延迟相关，影响响应速度。

- **Token 消耗大户。** 像 Playwright 这样的 MCP（模型上下文协议，一种让 AI 调用外部工具的标准协议）和图片输入会飞快地烧掉 token，让你在 Claude Code 里比预期更早进入「精简会话」状态。

- **工具太多的智能体。** 模型花在解析工具定义上的 token 比干正事还多。

更本质的一点是：**上下文工程没有消失，只是进化了。** 重心从「过滤掉坏的上下文」转向了「确保对的上下文在对的时机出现」。这个转变为 Level 4 铺好了路。

## Level 4：复利工程（Compounding Engineering）

![Compounding Engineering](/images/reading/agentic-engineering-3.jpg)

上下文工程改善的是当前这次会话。**复利工程改善的是之后的每一次会话。** 这个概念由 Kieran Klaassen 推广开来，对我和很多人来说都是一个拐点——它证明了「凭感觉编程」（Vibe Coding）能做的远不止原型开发。

这是一个「计划、委派、评估、固化」的循环。你为任务规划足够的上下文让 LLM 成功完成，然后委派给它，评估输出，最后——**关键步骤——把你学到的东西固化下来：** 什么有效、什么出了问题、下次该遵循什么模式。

这个「固化」步骤就是它能产生复利的原因。LLM 是无状态的。如果它昨天重新引入了一个你明确移除的依赖，明天它还会这么干——除非你告诉它不要。**最常见的方式是更新你的 CLAUDE.md**（或等效的规则文件），把教训烘焙进未来的每一次会话。但要小心：把所有东西都塞进规则文件的冲动会适得其反（指令太多跟没有一样）。更好的做法是创建一个让 LLM 能自己轻松发现有用上下文的环境——比如维护一个时刻更新的 docs/ 文件夹（Level 7 会详谈）。

**复利工程的实践者通常对输入给 LLM 的上下文极度敏感。** 当 LLM 犯了错,他们本能地先想是不是缺了什么上下文，而不是怪模型能力不行。这种直觉让 Level 5 到 8 成为可能。

## Level 5：MCP 与技能（Skills）

Level 3 和 4 解决的是上下文问题。**Level 5 解决的是能力问题。** MCP 和自定义技能让你的 LLM 能访问数据库、API、CI 流水线、设计系统、Playwright 做浏览器测试、Slack 发通知。模型不再只是思考你的代码库——**它现在能直接操作了。**

MCP 和 Skills 的介绍已经很多了，我就不重复了。但分享几个我的用法：我的团队共享一个 PR 审查技能，大家持续迭代（至今还在）。它会根据 PR 的性质有条件地启动子智能体：一个负责数据库集成安全检查，一个做复杂度分析以标记冗余或过度工程，一个检查 prompt 健康度确保符合团队标准格式，还会跑 linter 和 Ruff。

为什么在一个审查技能上投入这么多？**因为当智能体开始批量产出 PR 时，人工审查变成了瓶颈，而不是质量关卡。** Latent Space 有力地论证了代码审查正在走向死亡。自动化的、一致的、技能驱动的审查才是替代品。

在 MCP 方面，我用 Braintrust MCP 让 LLM 能查询评估日志并直接做修改；用 DeepWiki MCP 让智能体能访问任何开源仓库的文档，而不用手动拉进上下文。

当团队里多个人都在写同一个技能的不同版本时，**就该整合成共享注册表了。** Block（节哀）写了一篇很好的文章：他们建了一个内部技能市场，有 100 多个技能，按角色和团队打包推荐。技能和代码享受同等待遇：Pull Request、审查、版本历史。

还有一个趋势值得提：**LLM 越来越多地用 CLI 工具代替 MCP。**（好像每家公司都在发一个：Google Workspace CLI、Braintrust 也快了）。原因是 token 效率。MCP 服务器在每一轮对话都会把完整的工具定义注入上下文，不管智能体用不用。CLI 反过来：智能体执行一个精准的命令，只有相关输出进入上下文窗口。我大量使用 agent-browser 正是这个原因——而不是用 Playwright MCP。

在继续之前要强调一点。**Level 3 到 5 是后面所有层级的地基。** LLM 在某些事情上出奇地好，在另一些事情上出奇地差，你需要在堆叠更多自动化之前先培养出对这些边界的直觉。如果你的上下文是嘈杂的，prompt 不够明确或有误导，工具描述写得不好，那 Level 6 到 8 只会放大这些混乱。

## Level 6：工程脚手架与自动反馈循环

![Harness Engineering](/images/reading/agentic-engineering-4.jpg)

**这里才是火箭真正开始升空的地方。**

上下文工程关注的是模型看到什么。工程脚手架关注的是构建整个环境、工具链和反馈循环，**让智能体无需你干预就能可靠地工作。给智能体反馈循环，而不只是给编辑器。**

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航都接进了智能体运行时，让它能截屏、驱动 UI 路径、查询日志、验证自己的修复。给一个 prompt，智能体就能复现 bug、录制视频、实现修复。然后它通过驱动应用来验证，提交 PR，回应审查反馈，合并——**只有在需要判断力的时候才升级到人类。** 智能体不只是写代码，它能看到代码运行的结果，然后迭代——跟人类做的一模一样。

我的团队做的是技术故障排除的语音和聊天智能体，所以我开发了一个叫 converse 的 CLI 工具，让任何 LLM 都能和我们的后端端点对话，进行逐轮会话。LLM 改完代码，用 converse 对真实系统测试对话，然后迭代。**有时候这些自我改进循环会连续跑好几个小时。** 当结果可验证时这套方法特别强大：对话必须遵循这个流程，或者在这些情况下调用这些工具（比如升级到人类客服）。

实现这一切的核心概念是**反压机制**（Backpressure，源自分布式系统，指系统中自动约束和反馈的能力）：类型系统、测试、linter、pre-commit 钩子——**这些自动化反馈机制让智能体无需人工干预就能检测和纠正错误。** 如果你想要自主性，你就需要反压。否则你得到的就是一台垃圾生产机器。这也延伸到安全领域。Vercel 的 CTO 指出，智能体、它们生成的代码和你的密钥应该存在于不同的信任域中——因为日志文件中埋入的 prompt 注入攻击可能诱骗智能体泄露你的凭证，如果一切都在同一个安全上下文里的话。**安全边界就是反压：它约束的是智能体脱轨时能做什么，而不只是应该做什么。**

两个有用的经验：

- **设计追求吞吐量，而非完美。** 当每次提交都要求完美时，智能体会扎堆在同一个 bug 上，互相覆盖修复。不如容忍小的非阻塞性错误，在发布前做最终的质量审查。我们对人类同事也是这么做的。

- **约束 > 指令。** 一步步的 prompting（「先做 A，再做 B，然后做 C」）越来越过时了。在我的经验中，**定义边界比给清单更有效**，因为智能体会死磕清单，忽略清单以外的一切。更好的 prompt 是：「这是我要的东西，做到所有测试通过为止。」

工程脚手架的另一半是确保智能体能在没有你的情况下自主导航你的代码仓库。OpenAI 的做法是：**把 AGENTS.md 控制在大约 100 行**，作为目录指向其他地方的结构化文档，并把文档的新鲜度纳入 CI 流程，而不是依赖容易过时的临时更新。

当你把这一切都建好之后，一个自然的问题浮现了：如果智能体能验证自己的工作、导航代码仓库、在没有你的情况下纠正自己的错误——**你为什么还需要坐在椅子上？**

## Level 7：后台智能体（Background Agents）

![Background Agents](/images/reading/agentic-engineering-5.jpg)

**尖锐观点：计划模式正在死亡。**

Boris Cherny——Claude Code 的创造者——今天仍然有 80% 的任务从计划模式开始。但每一代新模型，规划后的一次通过成功率都在攀升。**我认为我们正在接近一个节点：计划模式作为一个单独的人工参与环节将逐渐消失。** 不是因为规划不重要，而是因为模型自己规划的能力已经够好了。重要的前提：这只在你做好了 Level 3 到 6 的工作之后才成立。如果你的上下文干净、约束明确、工具描述清晰、反馈循环紧密，模型就能在不需要你先审核计划的情况下可靠地规划。如果你没做这些工作，你还是得盯着计划。

要明确一点，规划本身作为一种实践不会消失，只是在改变形态。对新手来说，计划模式仍然是正确的入口（如 Level 1 和 2 描述的）。但在 Level 7 面对复杂特性时，「规划」看起来不像写一份分步大纲，而更像是**探索**：探测代码库、在工作树（Worktree）中原型化方案、映射解决方案空间。而且越来越多时候，后台智能体在替你做这些探索。

这很重要，因为这正是解锁后台智能体的关键。**如果智能体能生成靠谱的计划并执行，不需要你签字确认，它就能在你做别的事情时异步运行。** 这是从「我在手忙脚乱切多个标签页」到「工作在没有我的情况下进行着」的关键转变。

Ralph 循环（以创建者 Ralph 命名的一种自主编码循环）是流行的入门方式：一个自主智能体循环反复运行编码 CLI，直到所有 PRD（产品需求文档）项目完成，每次迭代都生成一个带有干净上下文的新实例。以我的经验，把 Ralph 循环跑对是很难的，PRD 的任何不充分或误导都会反噬。它有点过于即发即忘了。

你可以并行跑多个 Ralph 循环，但智能体越多，你就越意识到自己的时间花在了哪里：协调它们、排序工作、检查输出、推一推这个戳一戳那个。你不再写代码了。**你变成了一个中层管理者。** 你需要一个编排智能体来处理调度，让你能专注于意图而非后勤。

我重度使用的工具是 Dispatch——一个我写的 Claude Code 技能，把你的会话变成指挥中心。你待在一个干净的主会话里，工人智能体在隔离的上下文中干重活。调度器负责规划、委派和追踪，你的主上下文窗口保留给编排工作。**当工人卡住时，它会浮出一个澄清问题，而不是默默失败。**

Dispatch 在本地运行，适合快速开发——反馈更快、交互调试更方便、没有基础设施开销。Ramp 的 Inspect 是互补方案，适合更长时间运行的自主工作：每个智能体会话在云端的沙箱 VM 中启动，配备完整的开发环境。PM 发现一个 UI bug，在 Slack 标记一下，Inspect 就接手跑起来——哪怕你的笔记本已经合上了。代价是运维复杂度（基础设施、快照、安全），但你得到的是本地智能体无法匹敌的规模和可复现性。我的建议是两种都用。

**在这个层级有一个出乎意料的强大模式：不同的模型做不同的事。** 最好的工程团队不是由克隆人组成的，而是由思维方式不同、经历不同、优势不同的人组成的。LLM 也是同理。这些模型经过不同的后训练，性格有着显著差异。我常规操作是：用 Opus 做实现、Gemini 做探索性研究、Codex 做审查——**累积产出比任何单一模型独立工作都更强。** 想象群体智慧的代码版。

关键是，**你还需要把实现者和审查者解耦。** 这个我已经吃过太多次亏了：如果同一个模型实例既实现又评估自己的工作，它是有偏见的。它会忽略问题，告诉你所有任务都完成了——其实并没有。这不是恶意，跟你不能给自己的考试打分是一个道理。让不同的模型（或一个带有专门审查 prompt 的不同实例）来做审查。你的信号质量会大幅提升。

后台智能体还打开了 **CI 与 AI 结合的闸门**。一旦智能体能在没有人坐镇的情况下运行，就可以从你现有的基础设施触发它们：一个文档机器人在每次合并后重新生成文档，提 PR 更新 CLAUDE.md（我们在用，节省了大量时间）；一个安全审查器扫描 PR 并提交修复；一个依赖机器人真正升级包并跑测试套件，而不是只标记一下。好的上下文、复利规则、有能力的工具、自动反馈循环——现在自主运行。

## Level 8：自主智能体团队

**还没有人掌握这一层级**，但有几家在推进。这是活跃的前沿。

Level 7 是一个编排 LLM 以中心辐射式向工人 LLM 派发工作。Level 8 移除了这个瓶颈。**智能体之间直接协调**：认领任务、共享发现、标记依赖、解决冲突——不再需要所有事情都通过单一编排者路由。

Claude Code 的实验性 Agent Teams 功能是早期实现：多个实例在共享代码库上并行工作，每个队友在自己的上下文窗口中运行，直接相互通信。Anthropic 用 16 个并行智能体从零构建了一个能编译 Linux 的 C 编译器。Cursor 用数百个并发智能体跑了数周，从零构建了一个网页浏览器，并把自己的代码库从 Solid 迁移到了 React。

但仔细看你会发现接缝。Cursor 发现没有层级结构，智能体会变得风险厌恶、原地打转。Anthropic 的智能体不断破坏现有功能，直到加入 CI 流水线防止回归。**每个在这个层级实验的人都说同一句话：多智能体协调是一个困难问题，没有人接近最优解。**

说实话，我不认为模型已经准备好了应对大多数任务的这种自主程度。即使它们够聪明，目前仍然太慢、太费 token，在月球射击级项目（编译器、浏览器构建——令人印象深刻但远非干净）之外不经济。**对我们大多数人日常做的工作来说，Level 7 是杠杆所在。** 我不会惊讶 Level 8 最终成为主流模式，但现在我会把精力放在 Level 7（除非你是 Cursor，突破本身就是业务）。

## Level ?

不可避免的「接下来是什么」问题。

一旦你能熟练地编排智能体团队，界面就没理由只停留在文本上。**语音对语音**（甚至思维对思维？）与编码智能体交互——对话式的 Claude Code，而不只是语音转文字输入——是自然的下一步。看着你的应用，大声描述一系列修改，然后看着它们在眼前发生。

有一群人在追逐完美的一次出手：说出你要什么，AI 一次完美搞定。问题是这预设了我们人类精确地知道自己想要什么。**我们不知道。我们从来就不知道。** 软件一直都是迭代的，我认为它永远会是。只是它会变得容易得多，远远超越纯文本交互，而且快得多。

那么：你在哪一级？你在做什么来到达下一级？
