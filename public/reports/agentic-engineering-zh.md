# 智能体工程的 8 个等级 — Bassim Eledath

> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个等级里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

---

![The 8 Levels of Agentic Engineering](/images/reading/agentic-engineering-1.jpg)

AI 的编程能力远远跑在了我们驾驭它的能力前面。所以那些刷 SWE-bench（SWE-bench，AI 编码能力的标准测试基准）分数的努力，跟工程管理层真正在意的生产力指标对不上号。Anthropic 团队 10 天就能交付 Cowork 这样的产品，另一个团队用同样的模型连个 POC 都搞不定——区别在于一个团队弥合了能力和实践之间的差距，另一个没有。

这个差距不是一夜之间能弥合的。它分等级地逐步收窄，一共 8 个等级。读到这里的人大多已经过了前几级，但你应该渴望到达下一级，因为每升一级，产出都是质的飞跃，而且模型能力的每次进步都会进一步放大这些收益。

你应该关心这件事还有一个原因：多人协作效应。你的产出比你想象的更依赖队友的水平。假设你是 7 级大神，睡觉的时候后台智能体（Background Agents）就在帮你提交好几个扎实的 PR。但如果你的仓库合并前需要一个同事审批，而这位同事还在第 2 级手动审 PR，你的吞吐量就被卡死了。所以拉队友升级，就是在帮自己。

通过和很多团队及个人的交流，我总结出了这套 AI 辅助编程的进阶路径，虽然不是严格线性的：

## 第 1 和第 2 级：Tab 补全与智能 IDE

这两级我快速带过，主要是为了完整性。可以随意跳读。

一切始于 Copilot 和 Tab 补全。按一下 Tab，代码自动补全。很多人大概早就忘了这个阶段，而后来者可能直接跳过了。这种方式更适合老手——他们能先搭好代码骨架，再让 AI 填充细节。

Cursor 这样的 AI 原生 IDE 改变了游戏规则，它把对话接入了代码库，让跨文件编辑变得轻松得多。但天花板始终是上下文。模型只能在它"看得见"的范围内帮你，而恼人的是，它经常要么看不到该看的上下文，要么看了太多不该看的。

大多数停留在这个阶段的人也在尝试计划模式（Plan Mode）：把一个粗略的想法转化成给 LLM 的结构化分步计划，反复打磨，然后触发执行。在这个阶段效果不错，也是保持掌控感的合理做法。不过到了后面的等级，你会发现对计划模式的依赖越来越少。

## 第 3 级：上下文工程

![Context Engineering](/images/reading/agentic-engineering-2.jpg)

"上下文工程（Context Engineering）"是 2025 年的年度热词。它之所以成为一门学问，是因为模型在获得恰到好处的上下文时，终于能可靠地执行一系列指令了。嘈杂的上下文和不够具体的上下文一样糟糕，所以核心工作就是提高每个 token 的信息密度。"每个 token 都得为自己在 prompt 里的位置拼命"，这就是当时的信条。

实际操作中，上下文工程涉及的面比大多数人意识到的要广。它包括你的系统提示和规则文件（.cursorrules、CLAUDE.md）。它包括你怎么描述工具，因为模型会读这些描述来决定调用哪个。它包括管理对话历史，避免长时间运行的智能体聊着聊着就跑偏了。它还包括决定每一轮暴露哪些工具，因为选项太多会让模型晕头转向，就像人一样。

如今你不太听到上下文工程这个词了。天平已经倾向于能容忍更多噪音、能在更混乱的环境中推理的模型（更大的上下文窗口也有帮助）。但注意上下文消耗依然重要。几个仍然会踩坑的场景：

- 小模型对上下文更敏感。语音应用常用小模型，而上下文大小也影响首 token 延迟，直接关系到响应速度。

- token 消耗大户。像 Playwright 这种 MCP（Model Context Protocol，模型上下文协议——一种让 AI 调用外部工具的标准协议）和图片输入会飞速吃掉 token，让你在 Claude Code 里比预想更快进入"精简会话"（Compact session，Claude Code 中上下文过长时自动触发的精简会话状态）状态。

- 智能体接入了几十个工具，模型花在解析工具描述上的 token 比干正事还多。

更大的要点是：上下文工程并没有消失，只是进化了。重心从"过滤坏上下文"转向了"确保正确的上下文在正确的时机出现"。这个转变，正是第 4 级的前提。

## 第 4 级：复利工程

![Compounding Engineering](/images/reading/agentic-engineering-3.jpg)

上下文工程改善的是当前会话。复利工程（Compounding Engineering，类似复利效应——每一次改进都会累积到下一次，像利滚利一样越滚越大）改善的是此后的每一次会话。这个概念由 Kieran Klaassen 推广开来，对我和很多人来说都是一个拐点——原来"凭感觉编程（Vibe Coding）"远不止能做原型。

它是一个"规划、委派、评估、沉淀"的循环。你规划任务，提供足够的上下文让 LLM 成功。你委派给它。你评估产出。然后，关键的一步——你把学到的东西沉淀下来：什么管用、什么出了问题、下次该遵循什么模式。

"沉淀"这一步才是让它产生复利的关键。LLM 没有记忆。如果它昨天把一个你明确移除的依赖又加了回来，明天它还会这么干——除非你告诉它别这样。最常见的做法是更新你的 CLAUDE.md（或等效的规则文件），把教训固化到未来的每次会话中。提醒一句：什么都往规则文件里塞的冲动可能适得其反（指令太多等于没有指令）。更好的做法是创造一个让 LLM 能自行发现有用上下文的环境，比如维护一个及时更新的 docs/ 文件夹（第 7 级会详细展开）。

复利工程的实践者通常对输入给 LLM 的上下文极其敏感。当 LLM 犯错时，他们的第一反应是想上下文是不是缺了什么，而不是怪模型能力不行。这种直觉，正是第 5 到第 8 级的基础。

## 第 5 级：MCP 与技能

第 3 和第 4 级解决的是上下文。第 5 级解决的是能力。MCP 和自定义技能（Skills）让你的 LLM 能访问数据库、API、CI 流水线、设计系统，用 Playwright 做浏览器测试，用 Slack 发通知。模型不再只是"想"你的代码库，它现在能直接"动手"了。

关于 MCP 和技能的好文章已经很多，我就不重复概念了。说说我怎么用的：我们团队共享一个 PR 审查技能，大家一起迭代（现在还在迭代），它会根据 PR 的性质有条件地启动子智能体（Subagent）。一个负责数据库集成安全，一个做复杂度分析以标记冗余或过度设计，一个检查 prompt 质量以确保符合团队标准格式，同时还跑 linter 和 Ruff。

为什么在审查技能上投入这么多？因为当智能体开始批量产出 PR 时，人工审查就变成了瓶颈，而不再是质量关卡。Latent Space 有一篇很有说服力的文章论证：我们熟悉的那种代码审查已经死了。取而代之的是自动化的、一致的、由技能驱动的审查。

MCP 方面，我用 Braintrust MCP 让 LLM 能查询评估日志并直接修改。我用 DeepWiki MCP 让智能体能直接访问任何开源仓库的文档，不用手动拉进上下文。

当团队里好几个人在各自写同一个技能的不同版本时，就该合并到一个共享注册表了。Block（节哀）有一篇很好的文章讲这个：他们建了一个内部技能市场，超过 100 个技能，还有为特定角色和团队策划的套装包。技能和代码享受同等待遇：PR、审查、版本历史。

还有一个趋势值得提：LLM 越来越多地用 CLI 工具而不是 MCP（似乎每家公司都在出自己的：Google Workspace CLI，Braintrust 很快也要出）。原因是 token 效率。MCP 服务器每一轮都会把完整的工具描述注入上下文，不管智能体用不用。CLI 反过来：智能体执行一条有针对性的命令，只有相关输出进入上下文窗口。我大量使用 agent-browser 就是这个原因，而不是用 Playwright MCP。

继续之前说一件事。第 3 到第 5 级是后面所有等级的基础。LLM 在某些事情上好得出乎意料，在另一些事情上又差得离谱，你需要先对这些边界建立直觉，然后才能在上面叠加更多自动化。如果你的上下文嘈杂、prompt 不够精确或描述有误、工具描述写得马虎，第 6 到第 8 级只会把问题放大。

## 第 6 级：工程脚手架与自动反馈循环

![Harness Engineering](/images/reading/agentic-engineering-4.jpg)

火箭才真正点火升空。

上下文工程管的是模型看到什么。工程脚手架（Harness Engineering）管的是构建整个环境、工具链和反馈循环，让智能体不用你介入就能可靠地干活。给智能体的不只是编辑器，而是完整的反馈回路。

OpenAI 的 Codex 团队把 Chrome DevTools、可观测性工具和浏览器导航都接入了智能体运行时，让它能截图、驱动 UI 路径、查日志、验证自己的修复。只需一条 prompt，智能体就能复现 bug、录一段视频、实现修复。然后它会驱动应用来验证，开 PR，回应审查意见，合并——只在需要判断力的时候才上报。智能体不只是写代码，它能看到代码产生的效果并迭代改进，和人的工作方式一样。

我的团队做技术问题排查的语音和聊天智能体，所以我做了一个叫 converse 的 CLI 工具，能让任何 LLM 和我们的后端逐轮对话。LLM 改代码、用 converse 对着线上系统测试对话、然后迭代。有时候这种自我改进循环会连续跑好几个小时。当结果可验证时效果尤其强大：对话必须按这个流程走，或者在特定情况下调用特定工具（比如转接人工客服）。

支撑这一切的核心概念是反压（Backpressure，源自分布式系统，指系统内置的自动约束和纠错能力）：类型系统、测试、linter、pre-commit hook 这些自动反馈机制，让智能体不需要人工干预就能发现并修正错误。要自主性，就得有反压。没有反压，你得到的只是一台垃圾生产机器。这也延伸到安全领域。Vercel 的 CTO 提出，智能体、它们生成的代码、你的密钥应该分属不同的信任域——因为藏在日志文件里的一条 prompt 注入就可能骗智能体把你的凭据偷走，如果所有东西共享同一个安全上下文的话。安全边界就是反压：它约束的是智能体失控时"能做什么"，而不仅仅是"该做什么"。

两条有用的经验：

- **为吞吐量设计，而不是为完美设计。** 如果要求每次提交都完美无缺，智能体会反复纠缠同一个 bug，互相覆盖对方的修复。更好的做法是容忍小的非阻塞性错误，发布前再做一次整体质量把关。我们对人类同事也是这样要求的。

- **约束优于指令。** 一步一步的提示（"先做 A，再做 B，再做 C"）正在过时。我的经验是，定义边界比给清单管用，因为智能体会死盯着清单，清单上没有的一概忽略。更好的 prompt 是"这是我要的东西，做到通过所有测试为止"。

工程脚手架的另一半是确保智能体能自行导航你的代码仓库。OpenAI 的做法：把 AGENTS.md 控制在大约 100 行，作为目录索引指向其他结构化文档，并把文档新鲜度纳入 CI 流程，而不是靠随手更新然后慢慢过时。

当你把这些都建好之后，一个自然的问题就浮出水面了：如果智能体能自己验证工作、导航仓库、修正错误，你为什么还要坐在椅子上？

## 第 7 级：后台智能体

![Background Agents](/images/reading/agentic-engineering-5.jpg)

一个大胆的观点：计划模式正在消亡。

Boris Cherny，Claude Code 的创造者，现在仍然有 80% 的任务从计划模式开始。但随着每一代新模型的发布，经过规划后的一次成功率在持续攀升。我认为我们正在接近一个临界点：计划模式作为独立的人工介入步骤将逐渐消失。不是因为规划不重要，而是因为模型自己规划的能力越来越强了。重要前提：这只在你做好了第 3 到第 6 级的功课后才成立。如果上下文干净、约束明确、工具描述清楚、反馈循环紧密，模型不需要你先审一遍计划就能可靠地规划。如果你没做好这些，那你还是得盯着计划不放。

澄清一下，规划本身不会消失，只是形态在变。对新手来说，计划模式仍然是正确的起点（如第 1 和第 2 级所述）。但到了第 7 级处理复杂功能时，"规划"看起来不再像写分步大纲，更像是探索：探查代码库、在工作树（Worktree）里做方案原型、摸清解决方案的空间。而且越来越多的情况下，后台智能体在替你做这些探索。

这很重要，因为它恰恰是开启后台智能体的关键。如果一个智能体能生成靠谱的计划并独立执行，不需要你签字确认，它就能在你干别的事情的时候异步运行。这是从"我在好几个标签页之间来回切换"到"有些工作在自动推进"的关键转变。

Ralph 循环（Ralph Loop，以创建者 Ralph 命名的一种自主编码循环模式）是常见的入门方式：一个自主循环，反复运行编码 CLI 直到 PRD（PRD，产品需求文档）中的所有项完成，每次迭代都启动一个全新实例和干净的上下文。我的经验是，要把 Ralph 循环调好很难，PRD 里任何不够精确或描述有误的地方都会反噬。它有点太"发射后不管（Fire-and-forget）"了。

你可以并行跑多个 Ralph 循环，但智能体一多，你就会发现自己的时间到底花在哪了：协调它们、安排任务顺序、检查产出、推一推卡住的地方。你不再写代码了。你变成了一个中层管理者。你需要一个编排智能体来处理调度，好让你专注于意图而不是后勤。

我一直在重度使用的工具是 Dispatch，一个我写的 Claude Code 技能，它把你的会话变成指挥中心。你待在一个干净的主会话里，工人智能体在隔离的上下文中干活。调度器负责规划、委派和追踪，你的主上下文窗口留给编排。当工人遇到困难时，它会把澄清问题浮上来，而不是默默失败。

Dispatch 在本地运行，适合你想紧贴工作的快速开发：反馈更快、交互调试更方便、没有基础设施开销。Ramp 的 Inspect 是互补的方案，适合更长时间运行、更高自主度的工作：每个智能体会话启动在云端沙箱 VM 里，配备完整的开发环境。一个 PM 发现了 UI bug，在 Slack 里标记一下，Inspect 接手开始干——哪怕你电脑合着盖呢。代价是运维复杂度（基础设施、快照、安全），但你换来了本地智能体做不到的规模化和可复现性。我建议两种都用（本地和云端后台智能体）。

在这个等级还有一个出人意料的有效模式：用不同的模型干不同的活。最好的工程团队不是由一群克隆人组成的，而是由思维方式不同、经历不同、各有所长的人组成的。LLM 也是同样的道理。这些模型的后训练路径不同，性格倾向也有实质差异。我日常的做法是让 Opus 负责实现、Gemini 负责探索性研究、Codex 负责审查，综合产出比任何单一模型独立工作都更强。群体智慧的代码版。

还有至关重要的一点：必须把实现者和审查者分开。这个教训我吃过太多次亏了——如果同一个模型实例既实现又评估自己的工作，它会有偏见。它会轻描淡写地略过问题，然后告诉你所有任务都完成了，实际上并没有。这不是恶意，原理和你不能给自己的考试打分一样。让不同的模型（或者带有审查专用 prompt 的不同实例）来做审查。你的信号质量会大幅提升。

后台智能体还打开大门让你把 CI 和 AI 结合起来。一旦智能体能在无人值守的状态下运行，就从你现有的基础设施触发它们。一个文档机器人在每次合并后自动重新生成文档并提 PR 更新 CLAUDE.md（我们在用，省了大量时间）。一个安全审查机器人扫描 PR 并直接开修复。一个依赖升级机器人真的去升级包并跑测试套件，而不是只标记一下就完事。好的上下文、复利规则、得力的工具、自动反馈循环——现在都在自主运行了。

## 第 8 级：自主智能体团队

还没有人真正掌握这个等级，但已经有少数团队在往这个方向探索。这是当下最前沿的阵地。

在第 7 级，你有一个编排 LLM 以中心辐射式（Hub-and-spoke）模式把工作分发给工人 LLM。第 8 级去掉了这个瓶颈。智能体之间直接协调——认领任务、共享发现、标记依赖、解决冲突——不再需要所有事都经过一个中央编排者。

Claude Code 的实验性 Agent Teams（Claude Code 的实验性多智能体协作功能）是一个早期实现：多个实例在共享代码库上并行工作，每个队友有自己的上下文窗口，彼此直接通信。Anthropic 用 16 个并行智能体从零写了一个能编译 Linux 的 C 编译器。Cursor 用了上百个并发智能体跑了好几周，从零做了一个浏览器，还把自己的代码库从 Solid 迁移到了 React。

但仔细看，就能看到缝隙。Cursor 发现没有层级的话，智能体会变得畏缩，反复空转却没有进展。Anthropic 的智能体不断破坏现有功能，直到引入了 CI 流水线来防止回归。在这个等级实验的人都说同样的话：多智能体协调是个很难的问题，离最优还差得远。

老实说，我不认为模型对大多数任务已经准备好承担这种程度的自主性。就算它们够聪明，速度还是太慢、token 消耗还是太高，在编译器和浏览器这种登月级项目之外不具备经济性（确实令人印象深刻，但远谈不上成熟）。对我们大多数人的日常工作来说，第 7 级才是杠杆所在。我不会意外第 8 级最终成为主流模式，但现在我会把精力放在第 7 级（除非你是 Cursor，突破本身就是你的生意）。

## 第 ? 级

不可避免的"接下来呢"问题。

一旦你能顺畅地编排智能体团队，就没有理由让交互界面停留在纯文本。用语音对语音（甚至思维对思维？）跟你的编码智能体交流——对话式的 Claude Code，而不仅仅是语音转文字输入——是自然的下一步。看着你的应用，大声描述一连串修改，然后看着它们在眼前发生。

有一群人在追求完美的一次成型：说出你想要的东西，AI 一次完美生成。问题是这个前提假设我们人类清楚地知道自己想要什么。我们不知道。从来都不知道。软件开发从来都是迭代的，我认为永远会是。只是它会变得容易得多、远超纯文本交互、快得多。

所以：你在哪一级？你在做什么来进入下一级？
