# 智能体工程的 8 个段位 — Bassim Eledath

> 作者 Bassim Eledath 是实战派——他自己写了 Dispatch（一个 Claude Code 技能），专门用来编排多个 AI 智能体协同工作。不是纸上谈兵，是每天带着团队用 AI 写代码的人。文章发表在 2026 年 3 月，AI 编程工具从实验品变成生产力工具的转折点上。Anthropic 的人 10 天就把 Cowork 上线了，另一边用着一模一样的模型连个 POC 都跑不通——差距藏在这 8 个段位里。
>
> 对设计师和产品经理来说，这篇不是「程序员的事」。它画出的是**AI 协作的通用进化路径**——从单点工具到上下文管理，再到知识复利，最后走向自主运行。你用 AI 做设计、写文档、管项目，脚下踩的是同一条路。搞懂这 8 级，就能看清自己站在哪里、下一步该补什么、以及为什么有些人用 AI 效率翻十倍而你还在手忙脚乱。
>
> 全文最扎心的一句话：**「你的产出比你以为的更依赖队友的段位。」** 你已经是 Level 7 高手了，后台智能体趁你睡觉就把好几个 PR 提好了。但合并得同事审批，同事还在 Level 2 手动看代码——你的速度就被死死卡住了。这不是工具问题，是协作问题。AI 时代的团队效率，瓶颈在最慢的那个人身上。别光顾着自己进阶——拉队友一起上来，那才是真正的杠杆。

---

AI 写代码的能力进步太快，快到我们自己的使用方式跟不上了。SWE-bench 上的分数不断刷新，但工程团队真正关心的生产力指标并没有同步提升，原因就在这里。Anthropic 的团队用 10 天就做出了 Cowork 这个产品，而另一个团队用着同样的模型，连一个 POC 都跑不通。差距不在模型，在于一个团队已经把"模型能力"和"实际用法"之间的鸿沟填上了，另一个还没有。

这条鸿沟不会一夜之间消失。它是分阶段跨越的，一共 8 个阶段。读到这篇文章的你，大概率已经过了前面几级。但你应该迫切地想往上走，因为每往上一级，产出都是质的飞跃，而且模型能力每一次提升都会进一步放大这种增益。

![The 8 Levels of Agentic Engineering](/images/reading/agentic-engineering-1.jpg)

还有件事你可能没想到：你的效率不只取决于自己，还取决于队友在哪个段位。假设你已经是第 7 级的高手，晚上睡觉时后台智能体帮你提了好几个 PR。但你的仓库需要同事审批才能合并，而这位同事还停留在第 2 级，手动一个个看 PR，你的吞吐量就被卡住了。所以拉队友升级，本质上也是在帮自己。

跟很多在用 AI 辅助编程的团队和个人聊过之后，我总结出了下面这 8 个段位。顺序不是严格线性的，但大致方向如此。

## 第 1 & 2 级：Tab 补全与 Agent IDE

![Levels 1 & 2](/images/reading/agentic-engineering-2.jpg)

这两级快速带过，主要是记录一下来路。

一切从 Copilot 和 Tab 补全开始。按一下 Tab 键，代码自动补全。很多人可能早已忘了这个阶段，后来才入场的人甚至直接跳过了。这种模式更适合有经验的开发者，因为你得先搭好代码骨架，AI 才能帮你填充细节。

Cursor 这类以 AI 为核心的 IDE 改变了局面。它把聊天和代码库打通了，多文件编辑变得容易很多。但天花板始终是上下文。模型只能帮你处理它看得到的部分，而它经常要么看不到关键信息，要么看到了一堆不相关的东西。

处于这个阶段的人通常也在尝试 Plan Mode（计划模式）：先把模糊的想法变成结构化的分步计划，反复调整，然后交给 LLM 执行。在这个阶段，计划模式确实好用，能帮你保持对过程的掌控。不过到了后面几级，对计划模式的依赖会逐渐减少。

## 第 3 级：上下文工程 Context Engineering

![Context Engineering](/images/reading/agentic-engineering-3.jpg)

Context Engineering（上下文工程）是 2025 年的年度热词。它火起来的契机是模型终于能稳定地消化适量的指令和恰到好处的上下文了。噪音太多和信息不足一样糟糕，所以核心工作就是提高每个 token 的信息密度。当时的口号是："每个 token 都必须证明自己有资格出现在 prompt 里。"

实际操作中，上下文工程涉及的面比大多数人意识到的要广。它包括你的系统提示词和规则文件（.cursorrules、CLAUDE.md）。它包括你怎么描述工具，因为模型会读这些描述来决定调用哪个。它包括管理对话历史，防止长时间运行的智能体跑着跑着忘了前面在干嘛。它还包括控制每一轮暴露哪些工具给模型，因为选项太多会让模型犯晕，就像选项太多会让人犯晕一样。

现在上下文工程的讨论声量小了不少。天平已经倾向于那些能容忍更多噪音、在混乱场景中依然能推理的模型，更大的上下文窗口也有帮助。不过，注意上下文消耗依然重要，有几个地方还是会踩坑。

小模型对上下文更敏感。语音应用经常用小模型，而上下文越大，首 token 的响应时间越长，直接影响延迟。token 消耗大户也要注意，比如 Playwright 的 MCP 和图片输入，token 烧得飞快，在 Claude Code 里你会比预期更早进入"压缩会话"状态。还有那些挂了几十个工具的智能体，模型花在解析工具 schema 上的 token 比干正事还多。

更大的趋势是，上下文工程没有消失，只是进化了。重心从"过滤掉坏的上下文"转向了"确保对的上下文在对的时机出现"。这个转变，正好为第 4 级铺好了路。

## 第 4 级：复利工程 Compounding Engineering

![Compounding Engineering](/images/reading/agentic-engineering-4.jpg)

上下文工程让当前会话变得更好。Compounding Engineering（复利工程）让之后的每一次会话都变得更好。Kieran Klaassen 率先推广了这个概念，对我和很多人来说，它是一个转折点，让大家意识到 Vibe Coding（凭感觉编程）的能力远不止做做原型。

复利工程的流程是：计划、委派、评估、沉淀。你为任务提供足够的上下文让 LLM 能做好，然后委派给它。做完你评估输出。最关键的一步：把学到的东西沉淀下来。什么有效、什么出了问题、下次该遵循什么模式。

沉淀这一步才是"复利"的来源。LLM 没有记忆。你昨天明确删掉了某个依赖，它今天还会给你加回来，除非你告诉它不要这样做。最常见的方式是更新你的 CLAUDE.md（或等效的规则文件），把教训写进去，这样以后每一次新会话都能受益。不过有个提醒：什么都往规则文件里塞的冲动会适得其反，指令太多等于没有指令。更聪明的做法是营造一个环境，让 LLM 自己能方便地发现有用的上下文，比如维护一个时刻更新的 docs/ 文件夹（第 7 级会详细聊）。

习惯了复利工程的人，对喂给 LLM 的上下文特别敏感。LLM 犯了错，他们本能地先想"是不是上下文缺了什么"，而不是怪模型不行。**有了这种直觉，第 5 到第 8 级才走得通。**

## 第 5 级：MCP 与 Skills（技能）

![MCP and Skills](/images/reading/agentic-engineering-5.jpg)

第 3、4 级解决的是上下文问题。第 5 级解决的是能力问题。MCP 和自定义 Skills（技能）让你的 LLM 能访问数据库、API、CI/CD 流水线、设计系统，能通过 Playwright 做浏览器测试，能通过 Slack 发通知。模型从"想想你的代码库"变成了直接"动手操作"。

MCP 和 Skills 的入门材料已经很多，这里不再重复。说说我具体怎么用的。我们团队共享一个 PR 审查技能，大家持续迭代。它会根据 PR 的性质有条件地启动不同的子智能体：一个负责检查与数据库的集成安全，一个做复杂度分析找出冗余或过度设计，一个检查 prompt 是否符合团队规范，还会跑 Linter 和 Ruff。

为什么花这么大力气做一个审查技能？因为智能体开始批量生产 PR 之后，人工审查就成了瓶颈，而不是质量关卡。Latent Space 对此有个很有说服力的观点：**传统意义上的代码审查已经死了，取代它的是自动化的、一致的、技能驱动的审查。**

MCP 方面，我用 Braintrust MCP 让 LLM 直接查询评估日志并做修改。我用 DeepWiki MCP 让智能体能访问任何开源仓库的文档，不用手动把文档拉进上下文。

当团队里多个人都在写同一个技能的各自版本时，就该整合成一个共享的技能注册中心了。Block（原 Square）在这方面做得很好，他们写过一篇文章介绍内部经验：他们搭建了一个内部技能市场，有 100 多个技能，还为不同角色和团队整理了精选套装。技能享受和代码一样的待遇：PR、审查、版本记录。

还有一个趋势值得关注：越来越多的 LLM 开始用 CLI 工具代替 MCP，而且几乎每家公司都在发布自己的 CLI 工具，比如 Google Workspace CLI，Braintrust 也即将推出一个。原因是 token 效率。MCP server 在每一轮都会把完整的工具 schema 注入上下文，不管智能体用不用。CLI 则相反：智能体执行一条精准的命令，只有相关的输出进入上下文窗口。我大量使用 agent-browser 而不是 Playwright MCP，正是这个原因。

在往下走之前，有一点要强调。第 3 到第 5 级是后面所有内容的基础。LLM 在有些事情上好得出人意料，在另一些事情上差得出人意料，你需要培养对这些边界的直觉，才能在上面叠加更多自动化。如果你的上下文有噪音，prompt 写得不够清楚或有偏差，工具描述不到位，那第 6 到第 8 级只会把问题放大。

## 第 6 级：工程脚手架 Harness Engineering 与自动反馈循环

![Harness Engineering](/images/reading/agentic-engineering-6.jpg)

到了这一级，火箭真的开始起飞了。

上下文工程管的是模型看到什么。Harness Engineering（工程脚手架）管的是整个环境：工具链、反馈回路，让智能体能在你不介入的情况下可靠地干活。核心理念是：**给智能体一个反馈循环，而不只是一个编辑器。**

OpenAI 的 Codex 团队做了一个很好的示范。他们把 Chrome DevTools、可观测性工具和浏览器导航都接入了智能体运行时，让它能截图、操控 UI 路径、查询日志、验证自己的修复。给一个 prompt，智能体就能复现 bug、录制视频、实现修复。然后它通过操控应用来验证，提交 PR，回应审查意见，合并代码，只在需要判断的时候才升级给人类。智能体不只是写代码，它能看到代码跑出来的效果，然后迭代，跟人类的工作方式一样。

我的团队做的是语音和聊天类的技术支持智能体，所以我做了一个叫 converse 的 CLI 工具。它让任何 LLM 都能和我们的后端接口对话，进行多轮对话测试。LLM 改代码，用 converse 跑对话测试，看结果，再改，反复循环。有时候这种自我改进循环能跑好几个小时。当结果可以明确验证时，这种方式特别强大，比如"对话必须走这个流程"或者"在这些场景下必须调用这些工具"（比如升级到人工客服）。

支撑这一切的核心概念叫 Backpressure（反压机制）：类型系统、测试、Linter、pre-commit hook 这些自动化的反馈机制，让智能体自己发现和纠正错误，不需要人来干预。想要自主性，就必须有反压。否则出来的就是一堆垃圾。安全层面也一样。Vercel 的 CTO 提出了一个重要原则：智能体、它生成的代码、你的密钥，三者应该放在不同的信任域里。因为一条藏在日志文件里的 Prompt Injection（提示注入）可能骗智能体把你的凭证泄露出去，如果所有东西共享一个安全上下文的话。安全边界就是反压：它限制的是智能体失控时"能"做什么，而不只是"应该"做什么。

关于这一级，有两个实践心得。

第一，追求吞吐量，而不是每次提交都完美。要求每个 commit 都完美的话，多个智能体会在同一个 bug 上打转，互相覆盖对方的修复。更好的做法是容忍小的、不阻塞的问题，发布前统一做一轮质量检查。我们对人类同事也是这么做的。

第二，约束比指令好用。一步一步告诉智能体"先做 A，再做 B，再做 C"的方式已经过时了。我的经验是，定义边界比给清单有效，因为智能体会死盯着清单，清单上没有的事情一概忽略。更好的 prompt 写法是"这是我要的结果，做到通过所有这些测试为止"。

工程脚手架的另一半，是确保智能体不需要你也能在仓库里找到路。OpenAI 的做法是：AGENTS.md 控制在大约 100 行，充当目录索引，指向其他位置的结构化文档。同时把文档新鲜度检查纳入 CI，而不是依赖随手更新——随手更新迟早会过时。

当这一切都搭好之后，一个自然的问题浮现出来：如果智能体能验证自己的工作、在仓库里自主导航、自己纠错，你为什么还要坐在那里盯着？

## 第 7 级：后台智能体 Background Agents

![Background Agents](/images/reading/agentic-engineering-7.jpg)

一个大胆的判断：Plan Mode（计划模式）正在走向消亡。

Claude Code 的创造者 Boris Cherny 今天仍然有 80% 的任务从计划模式开始。但每一代新模型发布，规划后的一次通过率都在攀升。我认为我们正在接近一个临界点：计划模式作为一个需要人参与的独立步骤，即将逐渐消失。不是因为规划不重要，而是因为模型自己规划的能力越来越强。但有一个大前提：你得先把第 3 到第 6 级的工作做好。上下文干净、约束明确、工具描述清晰、反馈循环完善，模型才能在不需要你审核的情况下可靠地规划。如果这些基础没打好，你还是得盯着计划。

要说清楚的是，规划本身不会消失，只是形态在变。对新手来说，计划模式仍然是最好的入口（如第 1、2 级所述）。但到了第 7 级，面对复杂功能，"规划"已经不是写一份分步大纲了，更像是探索：深入代码库、在 worktree 里做原型实验、摸清解题空间。而且越来越多时候，这种探索工作是 Background Agents（后台智能体）在替你做。

这一点之所以关键，是因为它直接打开了后台智能体的大门。如果智能体能制定一个靠谱的计划并独立执行，不需要你签字确认，它就可以异步运行，你去做别的事。这才是从"我同时盯着好几个标签页"到"有些工作在我不在的时候自己在跑"的根本转变。

Ralph Loop 是最流行的入门方式。它是一个自主循环，反复运行编码 CLI，直到 PRD 里的所有条目完成为止。每轮迭代都会启动一个全新的实例，带着干净的上下文。不过我的经验是，Ralph Loop 调通不容易，PRD 写得稍有不清楚或遗漏，后面都会出问题。它有点太"点火就忘"了。

你可以并行跑多个 Ralph Loop，但智能体开得越多，你越会发现自己的时间花在了哪里：协调它们、安排顺序、检查输出、推一推进度。你已经不写代码了，你变成了中层管理。这时候你需要一个 Orchestrator（编排器）智能体来处理分发，这样你才能专注于意图层面，而不是陷在执行细节里。

我一直在重度使用的工具叫 Dispatch，这是我自己做的一个 Claude Code 技能。它把你的会话变成一个指挥中心。你留在一个干净的主会话里，工作者智能体在隔离的上下文中干活。Dispatch 负责规划、分发和跟踪，你的主上下文窗口只用来做编排。当某个工作者卡住时，它会浮现一个澄清问题，而不是悄悄失败。

Dispatch 在本地运行，适合你想贴近工作的快速开发：反馈更快，调试更方便，没有基础设施开销。Ramp 的 Inspect 则是另一种互补方案，适合更长时间运行、更自主的工作：每个智能体会话在云端的沙箱 VM 里启动，自带完整开发环境。一个 PM 在 Slack 里标记了一个 UI bug，Inspect 接手处理，你的笔记本电脑可以关上。代价是运维复杂度更高（基础设施、快照、安全），但你获得的是本地智能体做不到的规模和可复现性。我建议两种都用，本地和云端后台智能体各有其适用场景。

在这个段位，有一个出人意料的有效模式：**不同的工作交给不同的模型。** 最好的工程团队不是一群相同的人，而是一群思维方式不同的人，经历不同，各有所长。LLM 也一样。这些模型经过不同的后训练，性格和倾向有明显差异。我日常的做法是把实现交给 Opus，探索性研究交给 Gemini，代码审查交给 Codex，综合输出比任何单一模型都强。可以理解为"群体智慧"，但用在代码上。

另外一个关键经验是，实现者和审查者必须分开。我吃过太多次亏：如果同一个模型实例既写代码又审查自己的代码，它会有偏见。它会忽略问题，告诉你所有任务都完成了，其实并没有。这不是故意的，道理跟你不能给自己的考试打分一样。用另一个模型（或者用一个带有审查专用 prompt 的独立实例）来做审查，信号质量会大幅提升。

后台智能体还打开了 CI 与 AI 结合的大门。既然智能体可以在没人盯着的情况下运行，就让它们从你现有的基础设施触发。一个文档机器人在每次合并后自动重新生成文档，并提 PR 更新 CLAUDE.md，我们在用，省了大量时间。一个安全审查智能体扫描 PR 并直接提交修复。一个依赖管理智能体真的去升级包并跑完测试套件，而不是只标记一下。好的上下文、复利规则、强大的工具、自动反馈循环，现在全都自主运行了。

## 第 8 级：自主智能体团队 Autonomous Agent Teams

![Autonomous Agent Teams](/images/reading/agentic-engineering-8.jpg)

还没有人真正掌握这一级，但已经有一些团队在向这里突进。这是当前最前沿的探索区域。

在第 7 级，你有一个编排器 LLM 以辐射状（hub-and-spoke）向工作者 LLM 分派任务。第 8 级要去掉这个瓶颈。智能体之间直接协调：认领任务、共享发现、标记依赖、解决冲突，不再把所有事情都路由到一个中央编排器。

Claude Code 的实验性 Agent Teams 功能是一个早期实现：多个实例并行在共享代码库上工作，每个队友有自己的上下文窗口，彼此直接沟通。Anthropic 用 16 个并行智能体从零开始构建了一个 C 编译器，能编译 Linux。Cursor 让数百个并发智能体连续跑了数周，从零做了一个浏览器，还把自己的代码库从 Solid 迁移到了 React。

但仔细看，接缝处很明显。Cursor 发现如果没有层级结构，智能体变得保守，在原地打转没有进展。Anthropic 的智能体不断破坏已有功能，直到加了 CI 流水线来防止回归才好转。所有在这一级实验的人都说同一句话：多智能体协调是一个很难的问题，没有人接近最优解。

说实话，我认为当前的模型在大多数任务上还没准备好支撑这种程度的自主性。就算它们足够聪明，也还是太慢、太烧 token，在编译器和浏览器这种登月项目之外不太经济（这些项目确实很惊艳，但远远谈不上干净利落）。对我们大多数人日常做的工作来说，第 7 级才是杠杆最大的位置。我不排除第 8 级最终会成为主流模式，但现阶段我的精力会放在第 7 级，除非你是 Cursor 这样把突破本身当成商业目标的公司。

## 第 ? 级

接下来会怎样？

一旦你能顺畅地编排智能体团队，交互方式就没有理由必须停留在文字上。语音交互，甚至思维直连式的交互，跟你的编码智能体对话，不是语音转文字输入，而是真正的对话式 Claude Code。看着你的应用，大声描述一连串修改，然后看着它们在眼前发生。

有一群人在追求完美的"一次生成"：说清楚你要什么，AI 一轮就给出完美结果。问题是，这个前提假设我们人类知道自己到底要什么。我们不知道。从来都不知道。软件从来都是迭代的，我相信它永远都会是。只是迭代会变得容易得多，会远远超越纯文字的交互方式，而且会快得多。

所以：你在哪个段位？你在做什么来到达下一个？
